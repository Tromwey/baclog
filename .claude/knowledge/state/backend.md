## Convenciones vigentes
<!-- Las reglas que un agente debe respetar al tocar este dominio, con un ejemplo correcto/incorrecto si ayuda. -->
- **Las server actions son wrappers finos (2026-09-24).** Forma canónica: `assertUser()`/`assertOwnsBacklog()`/`assertOwnsUserItem()` → función de `src/modules/**` con `userId` explícito → `revalidatePath`/`redirect`. **Toda regla de negocio nueva va al módulo, nunca a la action**, porque `/api/v1` reutiliza el módulo y jamás llama a una action (redirigen, revalidan y asumen cookies). Si una action todavía tiene lógica propia, extraerla primero. Un módulo que recibe `userId` nunca lleva `"use server"`.
- **Un handler v1 nuevo** = `withApi(async (req, { user, params }) => …)` en `src/app/api/v1/**`, serializa con `_lib/wire/*` a un zod de `_lib/schemas.ts`, aparece en `ios/API.md` §4 y gana un caso en `scripts/api-smoke.ts` (en `reads` si no muta; en `writes`, antes del `writes.push(e1DeleteMe)`). Listas siempre en `{ items }`; `POST` que crea responde 200 con el recurso; errores solo vía `ApiError` (`reason` como sub-código, `fields` en español).
- **Antes de tocar el `select` de una query "fuente"**, `grep -rn "ReturnType<typeof <fn>>" src`: si alguien deriva un tipo de ella y lo construye por otro camino, agrega una query hermana (`getBacklogItemsWithState`) o un `Pick`, no columnas (learning `2026-09-24-campo-aditivo-en-select-rompe-tipos-construidos-a-mano.md`).

## Decisiones tomadas (y por qué)
<!-- Una línea por decisión de arquitectura viva, con la razón. Si se revierte, se reescribe la línea. -->
- **Los hechos de serie (estado/temporadas) se funden en `catalog_item.raw`, no en columnas (2026-09-03).** Migrar la DB compartida necesita al founder; el jsonb ya existe y el `/search/tv` guardado no trae esos campos. La frescura se lee de un marcador propio dentro de `raw` (`_series_facts_at`) y NO de `refreshed_at`, porque el upsert de búsqueda bumpea `refreshed_at` sin tocar `raw` (una re-búsqueda haría parecer frescos hechos de hace semanas). Series terminadas nunca se re-consultan; en emisión, cada 7 días.
- **Link-out de música: un resolver por servicio, fail-open al piso de búsqueda (2026-09-02).** Odesli («una llamada trae todo») murió; ahora cada servicio resuelve solo y un fallo transitorio (sin key, 429/5xx, timeout) devuelve la búsqueda SIN cachearla. Un link exacto equivocado es peor que una búsqueda: el matcher exige título y artistas iguales, nunca containment.
- **Spotify se queda en búsqueda profunda por ahora (2026-09-02).** Desde 2026-02 la Web API en Development Mode exige cuenta Premium del desarrollador, 1 Client ID y uso «no comercial»; la app quedó sin crear, pendiente de decisión del founder. YouTube Music no tiene API de álbumes: búsqueda por diseño.
- **Los links de música se cachean sin región** aunque la búsqueda de TIDAL use `countryCode` del viewer: los ids de álbum son globales; la disponibilidad por país es problema de la página de TIDAL, no nuestro.
- **`VISIBILITY`/`BacklogVisibility` viven en `modules/backlog/visibility.ts`, no en la action (2026-09-24).** La tabla estado → `(isPublic, showOnProfile)` la necesitan `collections.ts` y los handlers v1 sin importar un archivo `"use server"`; `backlog-actions.ts` la re-importa. El wire habla `private|link|profile` y se traduce con `visibilityFromWire`/`wireVisibilityOf`; `featured` sigue derivado, nunca persistido.
- **`getUserLibrary` es la única query de biblioteca (2026-09-24).** Perfil, recap (pantalla, card, cron) y `GET /me/titles` leen la misma fila por `user_item` con catálogo + `reviewId`; `(app)/recap/recap-data.ts` (la copia) se borró. Una lectura nueva "de toda la biblioteca" pasa por aquí.
- **La regla de estreno se aplica en servidor (2026-09-24).** `setMark` rechaza una marca sobre un título con `releaseDate > now` salvo `preview: true` ("La vi en preestreno"); en la web solo vivía en la UI (la barra de acciones se oculta). La API la exige porque un cliente nativo puede mandar lo que quiera.
- **Los timestamps de `user_item` solo se mueven si el valor cambia (2026-09-24).** `setMark` compara antes de escribir: un PUT repetido (la app reintenta) no re-estampa `obsessedAt` (instante de un evento del feed) ni `statusChangedAt` (bucket de era del recap).
- **La búsqueda distingue "sin resultados" de "catálogo caído" solo para la API (2026-09-24).** `unifiedSearchDetailed` reporta `failed`; la web sigue mostrando `[]` en ambos casos (postura previa), la API responde 503 `unavailable` únicamente cuando TODOS los proveedores pedidos fallaron y no volvió nada.
