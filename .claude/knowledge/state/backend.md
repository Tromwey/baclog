## Convenciones vigentes
<!-- Las reglas que un agente debe respetar al tocar este dominio, con un ejemplo correcto/incorrecto si ayuda. -->
- **Las server actions son wrappers finos (2026-09-24).** Forma canónica: `assertUser()`/`assertOwnsBacklog()`/`assertOwnsUserItem()` → función de `src/modules/**` con `userId` explícito → `revalidatePath`/`redirect`. **Toda regla de negocio nueva va al módulo, nunca a la action**, porque `/api/v1` reutiliza el módulo y jamás llama a una action (redirigen, revalidan y asumen cookies). Si una action todavía tiene lógica propia, extraerla primero. Un módulo que recibe `userId` nunca lleva `"use server"`.
- **Un handler v1 nuevo** = `withApi(async (req, { user, params }) => …)` en `src/app/api/v1/**`, serializa con `_lib/wire/*` a un zod de `_lib/schemas.ts`, aparece en `ios/API.md` §4 y gana un caso en `scripts/api-smoke.ts` (en `reads` si no muta; en `writes`, antes del `writes.push(e1DeleteMe)`). Listas siempre en `{ items }`; `POST` que crea responde 200 con el recurso; errores solo vía `ApiError` (`reason` como sub-código, `fields` en español).
- **Antes de tocar el `select` de una query "fuente"**, `grep -rn "ReturnType<typeof <fn>>" src`: si alguien deriva un tipo de ella y lo construye por otro camino, agrega una query hermana (`getBacklogItemsWithState`) o un `Pick`, no columnas (learning `2026-09-24-campo-aditivo-en-select-rompe-tipos-construidos-a-mano.md`).

## Decisiones tomadas (y por qué)
<!-- Una línea por decisión de arquitectura viva, con la razón. Si se revierte, se reescribe la línea. -->
- **La paleta de portada tiene UN camino de escritura: `fillCatalogPalette` (`modules/catalog/cache.ts`, 2026-09-25).** `UPDATE … WHERE palette_hex IS NULL` (el primero gana, nunca pisa; `[]` es no-op). Lo usan el add (`ensureUserItemAndMembership`, que también sirve al `PUT` de membresía de la API y a `onboarding/picks`), la action web de ver (`cacheItemPaletteAction`) y `PUT /api/v1/titles/{id}/palette`. Razón: la app iOS solo mostraba paletas; un título que nadie agregó desde la web quedaba gris en iOS para siempre. Un canal nuevo que escriba la paleta va por aquí, no con otro `update(catalogItems)`.
- **Fusionar cuentas es UN `db.batch` set-based, sin migración (2026-09-24, fase 4g).** El driver neon-http no permite leer entre sentencias de un batch, así que `mergeAccounts` es SQL de conjuntos (`UPDATE … WHERE NOT EXISTS`, `UPDATE … FROM`, `INSERT … SELECT … ON CONFLICT`, `DELETE`) en orden, con un guard al inicio (lock de las dos filas `user` + división por cero si falta alguna o es menor → rollback completo). Toda tabla con referencia a usuario tiene su regla escrita en `MERGE_COVERAGE`; el guardrail `check-merge-coverage` falla si aparece una tabla nueva sin decidir. Orden de estado en choques de `user_item`: `on_my_radar` < `in_progress` (= `custom`, deprecado y plegado en 0009) < `completed`, empate = destino (`STATUS_RANK`). Probado contra un Postgres 17 local desechable con 0000–0029 aplicadas y los datos sembrados a mano (el SQL capturado de `mergeAccounts` sin ejecutar nada en Neon): choques de estado/reseña/follow/bloqueo/avatar/medidor, limpieza de correo con `_` (no LIKE) y guard de menor abortando sin tocar nada.
- **El runtime de película también se funde en `catalog_item.raw` (2026-09-24, fase 4a)**, con marcador `_film_facts_at` y la misma razón que las series (sin migración). UNA consulta a TMDB por título: un runtime conocido no se re-consulta nunca; si TMDB aún no lo sabe (película sin estrenar, `runtime: 0`) o respondió **404** (película borrada/fusionada) se re-consulta a los 30 días, no en cada vista — antes un 404 no escribía marcador y cada vista de la ficha (la pública anónima incluida) llamaba a TMDB y logueaba error para siempre. Solo un fallo TRANSITORIO (sin key, 401/429/5xx, red) no escribe marcador (la siguiente vista reintenta; `warn`, no `error`). Un hecho nulo nunca se escribe como `null` en `raw`. `release_date` del detalle se queda también en `raw` (de ahí salió el backfill de la columna en la fase 4b).
- **La reseña propia no se repite en la paginación (2026-09-24, fase 4a).** Va fijada arriba en la ficha (`getItemReviewContext.own`, con `hidden`) y `getOthersReviewsPage` la excluye de TODAS las páginas, incluida `GET /titles/{id}/reviews` — así el cliente nunca deduplica.
- **Los hechos de serie (estado/temporadas) se funden en `catalog_item.raw`, no en columnas (2026-09-03).** Migrar la DB compartida necesita al founder; el jsonb ya existe y el `/search/tv` guardado no trae esos campos. La frescura se lee de un marcador propio dentro de `raw` (`_series_facts_at`) y NO de `refreshed_at`, porque el upsert de búsqueda bumpea `refreshed_at` sin tocar `raw` (una re-búsqueda haría parecer frescos hechos de hace semanas). Series terminadas nunca se re-consultan; en emisión, cada 7 días.
- **Link-out de música: un resolver por servicio, fail-open al piso de búsqueda (2026-09-02).** Odesli («una llamada trae todo») murió; ahora cada servicio resuelve solo y un fallo transitorio (sin key, 429/5xx, timeout) devuelve la búsqueda SIN cachearla. Un link exacto equivocado es peor que una búsqueda: el matcher exige título y artistas iguales, nunca containment.
- **Spotify se queda en búsqueda profunda por ahora (2026-09-02).** Desde 2026-02 la Web API en Development Mode exige cuenta Premium del desarrollador, 1 Client ID y uso «no comercial»; la app quedó sin crear, pendiente de decisión del founder. YouTube Music no tiene API de álbumes: búsqueda por diseño.
- **Los links de música se cachean sin región** aunque la búsqueda de TIDAL use `countryCode` del viewer: los ids de álbum son globales; la disponibilidad por país es problema de la página de TIDAL, no nuestro.
- **`VISIBILITY`/`BacklogVisibility` viven en `modules/backlog/visibility.ts`, no en la action (2026-09-24).** La tabla estado → `(isPublic, showOnProfile)` la necesitan `collections.ts` y los handlers v1 sin importar un archivo `"use server"`; `backlog-actions.ts` la re-importa. El wire habla `private|link|profile` y se traduce con `visibilityFromWire`/`wireVisibilityOf`; `featured` sigue derivado, nunca persistido.
- **`getUserLibrary` es la única query de biblioteca (2026-09-24).** Perfil, recap (pantalla, card, cron) y `GET /me/titles` leen la misma fila por `user_item` con catálogo + `reviewId`; `(app)/recap/recap-data.ts` (la copia) se borró. Una lectura nueva "de toda la biblioteca" pasa por aquí.
- **Fase 4d/4e/4f detrás de UN switch: `MIGRATION_0029_LIVE` (`src/auth/live-0029.ts`, hoy `false`) (2026-09-24).** El gate del bearer hace LEFT JOIN a `mobile_session` en CADA request: desplegar o correr el `next dev` compartido sin la tabla daría 500 en todo. Con el switch apagado el comportamiento es el de 4b (tokens sin `sid`, logout = solo `tv+1`), los endpoints de sesiones/dispositivos/`notifyFollowers` responden 503 y todo push es no-op con log; el login con Apple/Google funciona igual (usa `account`, que ya existe). Orden al migrar: `drizzle-kit migrate` → descomentar `notifyFollowers` en `schema.ts` → switch a `true` → deploy. El smoke parsea la línea y exige que coincida con la base.
- **Los efectos externos lentos van DESPUÉS de la respuesta (`afterResponse`, 2026-09-24).** Push de nuevo seguidor, `last_seen_at`, intercambio del código de Apple y revocación de Apple al borrar cuenta: ninguno puede bloquear ni tumbar la request que los provoca; sus errores solo van al log. El cron de estrenos sí espera su lote de push (ya corre fuera de cualquier request de usuario).
- **"No puede esperar" cubre video (founder, 2026-09-24, fase 4b).** El catálogo persiste el DÍA de TMDB (película `release_date`, serie `first_air_date` — el estreno del show; una temporada nueva NO es un estreno) en `catalog_item.release_date`, así que la marca da `409 not_released`, el feed/estantes/perfil muestran "no puede esperar" y el cron avisa también en video. **Semántica de la fecha:** un día de TMDB se guarda a las **06:00Z = 00:00 America/Mexico_City** (`RELEASE_DAY_UTC_HOUR`, UTC−6 fijo desde 2022): con `isUpcoming = releaseDate > now`, en CDMX el día del estreno deja de ser futuro justo a medianoche, nunca la tarde anterior (00:00Z = 18:00 CDMX del día previo) ni horas dentro del día (12:00Z daría 409 a las 02:00 CDMX a una marca que la app, que compara por día local, sí permite). Los álbumes conservan el instante de iTunes (07/08/12/00Z). **Toda fecha guardada cae dentro de su día UTC, así que las etiquetas de día se imprimen en UTC** (`release.ts` y `components/kura/tint.ts`, `STOREFRONT_TZ = "UTC"`; antes America/Los_Angeles, que imprimía el día anterior para 00Z/06Z) — igual que la app, que lee `day` por componentes UTC. Un INSTANTE que no es fecha de estreno (cuándo alguien guardó el título, en el correo) se imprime con `homeDayLong` (CDMX). El upsert hace `coalesce(excluded, actual)`: una fecha conocida corrige la vieja (TMDB mueve estrenos), un null nunca la borra. Guardrail: `scripts/check-wire.ts` ("releaseDayInstant…").
- **Marcar sin guardar crea el estado (founder, 2026-09-24, fase 4b).** `setMark` (`modules/backlog/state.ts`) sobre un título del catálogo sin `user_item` lo CREA (sin `backlog_item`: el mismo estado que deja borrar una colección) y aplica la marca; la app ofrece "guardar en" después. Orden: catálogo desconocido → `not_found`; `backfillPreorderDate` (la copia única de "entra a una biblioteca") y la regla de estreno ANTES del insert (un 409 no crea nada); `INSERT … ON CONFLICT DO NOTHING` + relectura (dos PUT en carrera convergen). `mark: null` sin `user_item` = `not_found`, nunca crea. Las actions web NO pasan por aquí (siguen sobre títulos guardados). Biblioteca, perfil, recap y `GET /me/titles` lo incluyen porque leen `user_item`; `GET /collections` no; `removeTitleFromLibrary` lo borra.
- **Baja del correo mensual = `users.notify_recap` (founder, 2026-09-24, fase 4b).** Una sola ruta de escritura: `updateProfile` (`modules/account/profile.ts`) detrás de `PATCH /me { notifyRecap }` y de `setNotifyRecapAction` (interruptor "Correo del recap mensual" en Ajustes › notificaciones, junto al de estrenos). Viaja en `USER_COLUMNS` (`src/auth/user-row.ts`) → `CurrentUser` → `Me`; jamás en `Person`.
- **La regla de estreno se aplica en servidor (2026-09-24).** `setMark` rechaza una marca sobre un título con `releaseDate > now` salvo `preview: true` ("La vi en preestreno"); en la web solo vivía en la UI (la barra de acciones se oculta). La API la exige porque un cliente nativo puede mandar lo que quiera.
- **Los timestamps de `user_item` solo se mueven si el valor cambia (2026-09-24).** `setMark` compara antes de escribir: un PUT repetido (la app reintenta) no re-estampa `obsessedAt` (instante de un evento del feed) ni `statusChangedAt` (bucket de era del recap).
- **La búsqueda distingue "sin resultados" de "catálogo caído" solo para la API (2026-09-24).** `unifiedSearchDetailed` reporta `failed`; la web sigue mostrando `[]` en ambos casos (postura previa), la API responde 503 `unavailable` únicamente cuando TODOS los proveedores pedidos fallaron y no volvió nada.

## Deuda conocida

- **Fase 4d/4e (2026-09-24)** — las filas revocadas de `mobile_session` no se borran nunca (crecen con cada login/logout; nada las lee salvo el gate por PK). Un token legado sin `sid` sigue vivo hasta su `exp` aunque su upgrade por `refresh` se revoque después (solo un logout lo mata). El push de estreno se manda en serie dentro del cron (un lote HTTP/2 al final, sin reintentos: un APNs caído ese minuto = ese push se pierde; el correo es la entrega de registro). Costo: menos links exactos; arreglo real = normalizar el catálogo al importar.
- **API v1 (2026-09-24)** — `DELETE /collections/{id}` no hace GC de `user_item` (igual que `deleteBacklogAction`): el título queda con estado y reseña pero sin colección.
