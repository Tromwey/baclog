## 0. Contexto y principios

- La app web (Next 16, `src/`) habla con el servidor por **server actions**. La app iOS (`ios/`, SwiftUI) habla con **la misma app desplegada** por HTTP: `src/app/api/v1/**` es la API, `ios/Kura/Services/LiveAPI.swift` el cliente. Un solo deploy, una sola base.
- **Misma verdad, mismo código.** Cada handler reutiliza `src/modules/**`; **ninguno llama a una server action** (redirigen, revalidan rutas y asumen cookies). Toda regla que la web tenía dentro de una action se extrajo a un módulo y la action pasó a ser un wrapper fino (`assert*` → módulo con `userId` explícito → `revalidatePath`/`redirect`). Regla desde ahora: **una regla nueva va al módulo, nunca a la action**, porque la API la reutiliza.
- **Autorización 100 % app-layer, igual que la web** (`AGENTS.md`): el usuario sale del bearer y solo del bearer (`requireApiUser` → `apiContext`); ningún handler acepta `userId` en body, query ni path; propiedad re-checada por mutación (`assertOwnsBacklog`, `assertOwnsUserItem` funcionan bajo bearer gracias a `AsyncLocalStorage`); lecturas cross-user solo por los módulos ya gateados (`public.ts`, `social/*`, `reviews/*`). La API **no abrió ninguna excepción nueva de authz**.
- **Sin migraciones hasta la fase 4b** (la primera es `0027_user_token_version_notify_recap`, aplicada el 2026-09-24: `users.token_version` §2.1 y `users.notify_recap` §4). Después: `0028_user_block` (4c) y `0029_device_sessions_push` (4d/4e: `mobile_session`, `device_token`, `follow_push_notice`, `users.notify_followers`), ambas generadas y pendientes de aplicar por el founder. Lo que el modelo no tiene (fijar, orden manual, portada elegida, visibilidad "seguidores", episodios vistos, notificaciones, solicitudes) queda fuera del contrato o responde `unsupported`; la app lo guarda local (`LocalPrefs`). Migrar la base Neon compartida (local = beta = prod) requiere confirmación del founder.
- El dominio sigue siendo `baclog.app`; la API vive en `https://baclog.app/api/v1`. La API es **aditiva**: desplegarla no toca la web.

## 1. Convenciones

- **Base** `/api/v1`. JSON UTF-8, claves **camelCase**, ids como string (UUID de la base; las personas se identifican por `handle`, nunca por id). Fechas **ISO 8601 UTC sin fracción de segundo** (`"2026-09-24T15:00:00Z"`, `isoDate()` en `schemas.ts`): el `JSONDecoder.iso8601` de Swift rechaza `.000Z`.
- **Errores**: `{ "error": { "code", "message", "reason"?, "fields"?, "retryAfterSeconds"? } }`.
  - `code` fijo: `unauthorized` 401 · `forbidden` 403 · `not_found` 404 · `invalid` 400 · `conflict` 409 · `rate_limited` 429 · `unsupported` 501 · `unavailable` 503 · `internal` 500.
  - `reason` = **sub-código opcional** sobre el que la app ramifica: `underage` (bajo `forbidden`), `not_released` y `reaction_required` (bajo `conflict`), `taken` (bajo `conflict`, username).
  - `fields` solo en `invalid`: `campo → mensaje`, **en español**, listo para pintar bajo el campo (viene de `ZodError` o del handler).
  - `message` es texto final en la voz Kura (qué pasó y qué hacer; sin guiño). Todo 401 es el MISMO cuerpo, falle lo que falle (sin header, firma, `aud`, `exp`, usuario borrado, menor): un 401 distinguible es un oráculo.
  - Headers: **`X-Request-Id`** en toda respuesta v1 (para correlacionar un reporte de la app con el log); **`Retry-After`** (segundos) en todo 429.
- **Paginación** keyset: `?cursor=<opaco>` → `{ items, nextCursor: string | null }`. Cursor **ausente** = página 1; cursor **corrupto** (no decodifica: la mitad de instante tiene que ser exactamente lo que emite el servidor, ISO 8601 UTC `YYYY-MM-DDTHH:MM:SS(.sss)Z` con año ≥ 2000) = `400 invalid` con `fields.cursor` — re-servir la página 1 en silencio escondería un bug del cliente como una primera página infinita. **No hay `limit`**: el tamaño de página lo fija el módulo (`FEED_EVENT_CHUNK` en el feed, la página de `getPeoplePage` en las listas de gente, `REVIEW_PAGE_SIZE`/`REVIEW_MORE_SIZE` en las reseñas de un título).
- **Envelopes**: **toda lista va en `{ items }`**, nunca un array desnudo. Las que paginan suman `nextCursor`; `me/following` y `me/followers` suman además `privateCount`. Ningún endpoint devuelve `null` a secas: lo opcional va envuelto (`{ event: FeedEvent | null }`).
- **Idempotencia** por clave natural: `PUT` = "poner en estado X" (membresía, marca, follow, reseña), `DELETE` = quitar; repetir no falla (un `DELETE` de algo que no existe es 204). Las escrituras devuelven el recurso resultante re-leído, no `{ ok }`. **Todos los `POST` que crean responden 200 con el recurso** (no 201).
- **Caché**: `Cache-Control: private, no-store` en toda respuesta v1 (éxito o error). Portadas: URLs de TMDB/mzstatic tal cual (ADR-007, hotlink); la app las carga con `AsyncImage`.
- **Versionado**: cambios incompatibles = `/api/v2`. Campos nuevos opcionales no rompen: los `Decodable` del iOS usan `decodeIfPresent` en todo lo opcional e ignoran claves desconocidas.
- **Rate limit**: 60 escrituras / 300 lecturas por minuto por usuario (`sub`), ventana deslizante **en memoria por instancia** (no global entre instancias de Vercel, no sobrevive un cold start; frena a un cliente desbocado, no es frontera de seguridad). `auth/*` limita por IP. Se evalúa **antes de leer la base** (la firma del token se verifica en CPU; la relectura del usuario viene después). Respuesta: 429 + `retryAfterSeconds` + `Retry-After`.
- **Runtime**: los handlers corren en Node (usan `node:async_hooks`), nunca en edge.

## 2. Autenticación

El web usa Auth.js v5 con JWT en cookie y el provider Credentials `otp` (`src/auth/config.ts`). Para móvil no hay cookies: se emite un **bearer propio** con las mismas garantías, ligado desde la fase 4d a una fila de `mobile_session` por instalación (§2.3). Tres formas de entrar, todas con la MISMA respuesta `{ token, user: Me }`: código por correo (§2.1), Apple y Google (§2.2).

### 2.1 Flujo OTP (implementado)

1. `POST /auth/otp/request` `{ email }` → `204`. Reusa `issueOtp` (`src/auth/otp.ts`; un código vivo por correo, cooldown de 60 s en DB). Cooldown → `429 rate_limited` con `retryAfterSeconds: 60`. 204 exista o no la cuenta (verify la crea; no hay nada que enumerar). Público, rate limit por IP (`withPublicApi`).
2. `POST /auth/otp/verify` `{ email, code, device: { platform: "ios", name, appVersion } }` → `{ token, user: Me }`. Reusa `verifyOtp` (crea el usuario si no existe, quema intentos, mata el código a los 5). Código malo/vencido → 401 (uno solo, nunca cuál). Cuenta menor → `403 forbidden` + `reason: "underage"`. `device` (`platform: "ios"`, `name` 1..120, `appVersion` 1..40) se guarda como la sesión de esta instalación (§2.3) y el bearer lleva su id como `sid`; el log estructurado lleva plataforma, versión, usuario y `sessionId`, nunca `device.name` (texto libre = PII). El `token` es un **JWS HS256 firmado con `AUTH_SECRET`**, `sub = user.id`, `aud = "kura-ios"`, `iat`, `exp = +30 días`, `jti` aleatorio (`issueMobileToken`, `src/authz/api.ts`). Distinto del JWE de Auth.js: la cookie no vale como bearer ni al revés.
3. `POST /auth/refresh` (bearer) `{ device? }` (body **opcional**: sin body, `{}` o `{ device }`) → `{ token, user: Me }`. **Solo rota cuando faltan < 7 días** para `exp`; si falta más, devuelve el **mismo** token que recibió. El token nuevo se acuña con el `tv` vigente y **el mismo `sid`**. Si llega `device` y el bearer tiene `sid`, actualiza nombre/versión de esa sesión (la app debería mandarlo al abrir: así una actualización de la app se ve en `GET /me/sessions`). **Token legado sin `sid`** (acuñado antes de 4d) con la migración 0029 viva: se le **crea sesión** (con `device` del body, o `platform "ios"`, `deviceName "iPhone"`, `appVersion "desconocida"` sin body) y se devuelve **siempre un token nuevo** con ese `sid`, falte lo que falte para `exp` — la app debe guardar el token que vuelve. Un refresh no revoca el viejo (muere en su `exp`, con el próximo logout de la cuenta o al revocar su sesión; un legado sin `sid` sigue vivo hasta su `exp`). La app lo llama al abrir (`AppStore.finishSplash`).
4. `POST /auth/logout` (bearer) → `204`. **"Cerrar sesión en todos lados"** (fase 4b, decisión del founder): incrementa `users.token_version` en una sola sentencia atómica (`token_version + 1`). Desde ese instante **todos** los bearers de la cuenta, de cualquier dispositivo, todo handoff web pendiente **y toda cookie web de Auth.js de la cuenta** (incluida la que abrió un handoff en el `SFSafariViewController`, y la de cualquier navegador donde se haya entrado con código) dan lo mismo que "sin sesión": 401 en v1, redirect a `/login` en la web. La cookie lleva su propio `tv` (lo pone `authorize`, lo copia el callback `jwt`) y `getCurrentUser` (`src/auth/session.ts`) lo compara con `token_version` en la MISMA relectura de la fila que ya hacía; una cookie de antes de 4b no trae `tv` y cuenta como 0. Es a nivel **cuenta** (decisión del founder, se mantiene tras 4d): además de subir `token_version`, marca **todas** las sesiones de `mobile_session` como revocadas y borra **todos** los `device_token` de la cuenta, en una sola transacción (`logoutEverywhere`, `src/auth/mobile-sessions.ts`) — ningún iPhone sigue recibiendo push de una cuenta de la que salió. Para sacar UN dispositivo está `DELETE /me/sessions/{id}` (§2.3). El "cerrar sesión" de la web solo borra la cookie de ese navegador (no incrementa la versión). Llamarlo con el token que acaba de revocar es 401; con un token nuevo vuelve a incrementar (mismo efecto). Activo desde el 2026-09-24 (migración 0027 aplicada, `TOKEN_VERSION_LIVE = true` en `src/auth/user-row.ts`; la constante queda como kill-switch documentado: en `false` logout vuelve a ser el no-op de antes y todo `tv` se compara contra 0).
5. `POST /auth/web-session` (bearer) `{ to? }` → `{ url }` (fase 4b). Devuelve una URL **absoluta, de un solo uso, que vive 60 s**, `<origen>/api/auth/handoff?t=<jws>&to=<path>`. Abierta en un `SFSafariViewController`, deja la web **ya autenticada** (cookie de Auth.js) y redirige a `to`. Sirve para las pantallas que solo existen en web; hoy es la tarjeta del recap (`/recap/tarjeta`, el exportador). `to` es opcional (por defecto `/recap/tarjeta`) y tiene que salir de una **lista blanca**: `/recap/tarjeta` y `/recap`, los dos con `?mes=YYYY-MM` opcional (`/` salió de la lista en 4b: la app no lo usa y cada destino extra amplía lo que puede hacer un handoff plantado). Cualquier otra cosa (URL absoluta, `//host`, `\`, otro path u otro param) → `400 invalid` + `fields.to`; nunca se "limpia" en silencio. Rate limit de escritura normal. **La URL no se comparte**: es una credencial de un uso. La app la abre directo, y `SFSafariViewController` tiene su propio cookie jar, no el de Safari.

**Bearer**: JWS HS256 (`AUTH_SECRET`) con `sub`, `aud = "kura-ios"`, **`tv`** (= `users.token_version` al acuñar), **`sid`** (= `mobile_session.id`, fase 4d), `iat`, `exp = +30 días` y `jti`. Lo acuñan `otp/verify`, `auth/apple`, `auth/google` y `refresh`, siempre con el `tv` vigente de la cuenta. Un token de antes de 4b no trae `tv` y cuenta como 0 (el default de la columna): sobrevive hasta el primer logout de su cuenta. Un `tv` presente que no sea entero ≥ 0 → 401. Un token sin `sid` (antes de 4d, o acuñado mientras la migración 0029 no está viva) es válido como hasta ahora hasta su `exp`; un `sid` presente que no sea un UUID → 401.

**Handoff (`GET /api/auth/handoff?t&to`, FUERA de v1, sin bearer)**: `t` es un JWS HS256 con `aud = "kura-web-handoff"`, `sub`, `tv`, `jti` y `exp = +60 s`. El `aud` impide que un bearer iOS sirva como `t`, y al revés. Al acuñarlo, el `jti` se registra en `verificationToken` (`identifier = "handoff:" + jti`), así que no hace falta una tabla nueva. La ruta primero valida `to` contra la lista blanca, antes de tocar el token. Después llama a `signIn("otp", { handoff: t })` de Auth.js. El provider Credentials `otp` tiene dos modos: `{ email, code }` (el de siempre, intacto) y `{ handoff }`. En modo `{ handoff }`, `authorize` verifica firma, `aud`, `exp` y el **`DELETE … RETURNING`** de la fila (un solo uso), y además que el `tv` siga siendo el vigente. El consumo vive dentro de `authorize` y no en la ruta porque el callback `POST /api/auth/callback/otp` también es alcanzable directo. El JWS exige `exp`, `jti` y `sub` (`requiredClaims`: uno firmado sin `exp` no vale). Si todo pasa, responde 302 a `to` con la cookie de Auth.js, que lleva el `tv` de la cuenta. **Cualquier** fallo (URL usada, vencida, manipulada, bearer como `t`, `to` fuera de lista, `tv` viejo, navegación cross-site, error del servidor) responde lo mismo: 302 a `/login`, sin cookie. El motivo va **solo al log del servidor**: `[auth/handoff] rid=<uuid> reason=<bad_signature|bad_aud|expired|used|no_user|tv_mismatch|db_error|bad_to|no_token|cross_site>` (un fallo del servidor, `CallbackRouteError`, se loguea como error con `reason=server_error`); el mismo `rid` viaja en `X-Request-Id` de la respuesta. **Mitigación de login-CSRF**: si el navegador manda Fetch Metadata y la navegación no es de primer nivel iniciada por el usuario (`Sec-Fetch-Site` ≠ `none` o `Sec-Fetch-Mode` ≠ `navigate`), se rechaza **sin consumir el token**; sin esos headers (clientes viejos) pasa. El `SFSafariViewController` abierto por la app manda `none` + `navigate`. Las respuestas llevan `Cache-Control: private, no-store` y `Referrer-Policy: no-referrer`, y hay rate limit por IP; el 429 es una página HTML mínima en español ("demasiados intentos"), porque quien la ve es una persona en un navegador. Diseño y riesgos aceptados (token en query string, login-CSRF acotado a 60 s) en `src/authz/handoff.ts` y `.claude/knowledge/state/security.md`.

`requireApiUser(request)` (`src/authz/api.ts`): lee `Authorization: Bearer`, verifica firma/alg/aud/exp/forma de `tv` y `sid`, **relee `users` por `sub` en cada request** con `loadUserForBearer` (`src/auth/user-row.ts`: la misma lista de campos que la cookie, nunca `birthYear`, más `token_version` y, si el token trae `sid`, un **LEFT JOIN a `mobile_session` en la MISMA query** — `id = sid AND user_id = sub`, sin segunda query por request) y devuelve el mismo `CurrentUser` que `requireUser()`. Cuenta borrada, `isMinor`, `tv` ≠ `token_version`, o `sid` cuya sesión no existe / es de otra cuenta / está revocada → 401 aunque la firma sea válida (la revocación es la relectura). `withApi` envuelve **todo** handler v1: `requireBearer` (401 sin DB) → rate limit por `sub` → relectura + `tv` (401 si la fila no está, es menor o el token es de antes del último logout) → `apiContext.run({ user }, handler)` → errores al contrato (con `rid`, método y ruta en el log) → `no-store` + `X-Request-Id`. `getCurrentUser()` consulta `apiContext` **antes** de `auth()`, así que dentro de un request v1 jamás se lee la cookie y `assertUser`/`assertOwnsBacklog`/`assertOwnsUserItem` funcionan sin cambios. `GET /me` pasa por `assertUser()` a propósito para que el puente se ejercite en cada smoke.

`readApiUser(request)` (misma comparación de `tv`) es el gemelo suave para rutas **fuera** de v1 que sirven web y app: hoy solo `/api/avatar/[key]`, que acepta **bearer además de cookie** (la app carga su propia foto sin cookie; mismo gate, mismo 404).

### 2.2 Sign in with Apple / Google (fase 4f, implementado)

Las dos rutas son **públicas** (`withPublicApi`, rate limit por IP como `otp/*`) y responden **exactamente lo mismo que `otp/verify`**: `{ token, user: Me }` (bearer con `sid`, sesión nueva por instalación). Cuenta menor → el mismo `403 forbidden` + `reason: "underage"`. `device` = `{ platform: "ios", name, appVersion }`, el mismo `DeviceSchema` que OTP. Todo fallo del token es **un solo 401** (nunca cuál).

1. `GET /auth/providers` (público, sin bearer) → `{ apple: boolean, google: { clientId: string } | null }`. La app pinta **solo** los botones que funcionan en este deploy: `apple` es `true` siempre salvo el kill-switch `AUTH_APPLE_DISABLED` (verificar un identity token de Apple no necesita llave); `google` es `null` sin `GOOGLE_IOS_CLIENT_ID` (el client id no es secreto: va dentro de cada build iOS, y la app lo necesita para `GIDConfiguration`).
2. `POST /auth/apple` `{ identityToken, rawNonce, authorizationCode?, fullName?: { givenName?, familyName? } | null, device }` → `{ token, user: Me }`.
   - `identityToken` se verifica contra el JWKS de Apple (`https://appleid.apple.com/auth/keys`, cacheado por instancia), RS256, `iss = https://appleid.apple.com`, `aud = com.tromwey.kura`, `exp`, y **`nonce` = SHA-256 hex de `rawNonce`** (la app genera `rawNonce`, manda `sha256hex(rawNonce)` en `ASAuthorizationAppleIDRequest.nonce` y el crudo aquí). Cualquier fallo → `401 unauthorized` "No pudimos confirmar tu cuenta de Apple…".
   - Cuenta: `account(provider = "apple", providerAccountId = sub)` → ese usuario. Si no existe y el token trae `email` con `email_verified` (booleano o `"true"`): se **liga** a la cuenta con ese correo si existe, o se **crea** (misma ruta que OTP: `findOrCreateUserByVerifiedEmail` en `src/auth/otp.ts` — badge de fundador y waitlist incluidos), y se inserta la fila `account`. Sin link y sin correo verificado → el mismo 401. Apple solo manda el correo en la PRIMERA autorización: de ahí en adelante manda el `account`.
   - **`fullName` se acepta y se IGNORA (desviación deliberada del brief)**: escribir `users.name` pondría `Me.onboardingComplete = true` y la app se saltaría el paso de onboarding que pide el **año de nacimiento** (el gate de edad F2.2). La app debe **pre-llenar** el campo de nombre del onboarding con `fullName` (Apple solo lo da la primera vez, del lado del cliente); `POST /me/onboarding { name, birthYear }` sigue siendo quien lo guarda.
   - `authorizationCode` (opcional pero **mándalo siempre**): después de responder, el servidor lo intercambia en `https://appleid.apple.com/auth/token` (`client_secret` = JWT ES256 `iss` team, `sub` bundle, `aud` appleid, `kid`) y guarda el `refresh_token` en `account.refresh_token`. Es lo que permite **revocar el vínculo con Apple al borrar la cuenta** (App Store 5.1.1(v), ver `DELETE /me`). Sin las env `APPLE_*` el login funciona igual y el intercambio se salta con log.
   - Kill-switch `AUTH_APPLE_DISABLED=1` → `503 unavailable` "Apple no está disponible por ahora. Entra con tu correo."
3. `POST /auth/google` `{ idToken, device }` → `{ token, user: Me }`. Verifica contra el JWKS de Google (`https://www.googleapis.com/oauth2/v3/certs`), RS256, `iss` ∈ {`https://accounts.google.com`, `accounts.google.com`}, `aud = GOOGLE_IOS_CLIENT_ID`, `exp`, y **`email_verified` true obligatorio** (con `email`). Mismo flujo de `account(provider = "google")` + ligado/creación por correo verificado. Sin `GOOGLE_IOS_CLIENT_ID` → `503 unavailable` "Google no está disponible por ahora." (y `auth/providers` ya dijo `google: null`).

**Cuenta ligada**: el correo de la cuenta Kura **nunca cambia** por un proveedor (una cuenta creada con OTP que luego entra con Apple conserva su correo; una creada con Apple guarda el correo que Apple dio, que puede ser un relay `@privaterelay.appleid.com`). Riesgo aceptado del ligado por correo verificado: `state/security.md`.

### 2.3 Sesiones por dispositivo (fase 4d, implementado)

Cada inicio de sesión (OTP, Apple, Google, o el `refresh` que mejora un token legado) crea una fila en `mobile_session` (`id` uuid, `platform`, `device_name`, `app_version`, `created_at`, `last_seen_at`, `revoked_at`) y el bearer lleva su `id` como `sid`. `last_seen_at` se actualiza **como mucho una vez cada ~10 min por sesión**, después de responder (condición en el UPDATE, sin escribir en el camino crítico).

- `GET /me/sessions` → `{ items: [MobileSession] }` — solo las **no revocadas**, `lastSeenAt desc`. `MobileSession = { id, platform, deviceName, appVersion, createdAt, lastSeenAt, current: boolean }` (`current` = la sesión del bearer que pregunta; un bearer legado sin `sid` ve todas en `false`). `deviceName` es el texto que mandó la app: solo lo ve su dueño.
- `DELETE /me/sessions/{id}` → `204`. Revoca esa sesión y **borra sus `device_token`** (una transacción). El siguiente request de esa app es `401`. **La sesión actual también se puede revocar** (este mismo bearer muere). Ajena, inexistente, malformada **o ya revocada** = el **mismo 404** "No encontramos esa sesión…" (la app debe tratar un 404 aquí como "ya no está").
- `POST /auth/logout` sigue siendo "en todos lados" (§2.1 paso 4).

**Mientras la migración 0029 no esté aplicada** (`MIGRATION_0029_LIVE = false` en `src/auth/live-0029.ts`): los logins acuñan tokens **sin `sid`** (sin fila), el gate ignora cualquier `sid`, `refresh` sigue la regla de ventana de 4b, y `GET /me/sessions`, `DELETE /me/sessions/{id}`, `PUT|DELETE /me/devices/{apnsToken}` y `PATCH /me { notifyFollowers }` responden **`503 unavailable`** con mensaje en español. La app debe tolerarlo (ocultar "Dispositivos", reintentar el registro de push en el siguiente arranque).

### 2.4 Push: dispositivos y avisos (fase 4e, implementado)

- `PUT /me/devices/{apnsToken}` `{ environment: "sandbox" | "production" }` → `204`. `apnsToken` = el token de APNs en **hex, 64..200 caracteres** (se guarda en minúsculas); otra cosa → `400 invalid` + `fields.token`; `environment` inválido → `fields.environment`. Upsert: si el token ya era de **otra cuenta**, pasa a la actual (el teléfono cambió de dueño o de sesión); queda ligado a la sesión del bearer (`sid`), así que revocar esa sesión o hacer logout lo borra. `environment` = `sandbox` en builds de Xcode/Debug, `production` en TestFlight/App Store.
- `DELETE /me/devices/{apnsToken}` → `204` idempotente; solo borra si el token es del caller (ajeno o desconocido = el mismo 204).
- `Me.notifyFollowers: boolean` (default `true`) + `PATCH /me { notifyFollowers }` (booleano estricto como `notifyRecap`: `"no"` → 400 `fields.notifyFollowers`). Preferencia propia: nunca en `Person`.
- **Avisos que envía el servidor** (APNs HTTP/2 a `api.push.apple.com` o `api.sandbox.push.apple.com` según `environment`, `apns-topic: com.tromwey.kura`, `apns-push-type: alert`; payload `{ aps: { alert: { title, body? }, sound: "default" }, kura: { … } }`):
  - **Estreno** (cron diario de estrenos, a quien le sale el correo — `notifyReleases`, guardado antes del estreno, una sola vez por título): `title` = "{título} ya salió ✦", `body` = la primera línea del correo ("Hoy sale {título}, de {artista}." en álbum; "Hoy sale {título}." en video), `kura: { type: "release", titleId }`.
  - **Nuevo seguidor** (solo cuando la arista es NUEVA, no en un re-follow idempotente; solo si quien sigue es un perfil **público con handle** y el seguido tiene `notifyFollowers`; máximo **uno por par cada 24 h**, así que dejar de seguir y volver a seguir no vuelve a sonar): `title` = "@{handle} te sigue", sin `body`, `kura: { type: "follower", handle }`.
- Un token que APNs responde `410` o `BadDeviceToken`/`Unregistered` se borra solo. Sin las env `APPLE_TEAM_ID`/`APPLE_KEY_ID`/`APPLE_PRIVATE_KEY` (o sin la migración 0029) el envío es un no-op con log `[push] …`: los endpoints de registro funcionan igual (con la migración) y nada falla.
- `GET /me/notifications` → sigue sin existir (sin modelo de bandeja).

## 4. Endpoints

Todos bajo `/api/v1`, todos con bearer salvo `auth/otp/*`. Entre paréntesis, el módulo que se reutiliza.

**Auth** — ver §2.1 (OTP, refresh, logout, web-session) y §2.2 (`auth/providers`, `auth/apple`, `auth/google`). **Sesiones y dispositivos** — ver §2.3 (`GET /me/sessions`, `DELETE /me/sessions/{id}`) y §2.4 (`PUT|DELETE /me/devices/{apnsToken}`).

**Cuenta**
- `GET /me` → `Me` (`assertUser` + `_lib/me.ts`).
- `PATCH /me` `{ name?, preferredService?, notifyReleases?, notifyRecap?, notifyFollowers?, isPublic? }` → `Me` re-leído (`modules/account/profile.ts` `updateProfile`, misma validación que las cinco actions; campo ausente = intacto; body vacío = no-op que devuelve `Me`). `notifyRecap` (fase 4b) es un booleano estricto como `notifyReleases`: `"no"`, `0` o `null` → `400 invalid` + `fields.notifyRecap`. En `false`, el cron mensual (`api/cron/recap`) no te incluye ni reclama tu mes; la web lo cambia en Ajustes › notificaciones ("Correo del recap mensual"). `notifyFollowers` (fase 4e) igual de estricto; **mientras la migración 0029 no esté viva un PATCH que lo incluya responde `503 unavailable` y no escribe NINGÚN campo** (la web no tiene interruptor para él).
- `GET /me/username/check?u=` → `{ status: "free" | "taken" | "invalid" }` (`modules/account/username.ts` `checkUsername`; lo malformado o reservado es `invalid`, no 400 — el campo se escribe en vivo; el propio handle actual lee `free`).
- `PUT /me/username` `{ username }` → `Me` (`claimUsername`; F2.17: reclamar pone `isPublic = true`). 400 `invalid` + `fields.username` si nunca podrá reclamarse (forma o `RESERVED`); `409 conflict` + `reason: "taken"` si alguien lo tiene.
- `POST /me/onboarding` `{ name, birthYear }` → `Me` (`modules/account/onboarding.ts` `completeOnboarding`; F2.2). Menor de 13 → la cuenta queda bloqueada (este bearer y todo login futuro son 401) y responde `403 forbidden` + `reason: "underage"`.
- `POST /me/onboarding/picks` `{ titles: [{ id?, externalRef?, paletteHex? }] }` (1..3) → `{ collection: Collection }` (`modules/backlog/picks.ts` `completePicks`: "Obsesiones" o la colección más reciente en re-entrada; todos los títulos se resuelven ANTES de escribir; uno no cacheado → 404 sin escribir nada).
- `GET /me/onboarding/people` → `{ items: [Person] }` (`modules/social/people.ts`; sin picks → `items: []`; `why` = "Le obsesiona {título}").
- `PUT /me/avatar` → `Me` con el `avatarUrl` nuevo. Acepta **multipart/form-data con parte `file`** o **body raw con `Content-Type: image/webp | image/jpeg | image/png`**, **≤ 400 KB** (`AVATAR_MAX_BYTES`); el servidor sniffea magic bytes (`modules/avatar/write.ts` `storeAvatar`, SVG jamás). `DELETE /me/avatar` → `Me` con `avatarUrl: null` (idempotente).
- `DELETE /me` → `204` (`modules/account/delete.ts`; cascadea todo, incluidas sesiones, `device_token` y el `account` de Apple/Google; el bearer queda revocado en la siguiente relectura — la app olvida el token). **Fase 4f**: si la cuenta tiene vínculo con Apple y guardamos su `refresh_token`, se revoca en `https://appleid.apple.com/auth/revoke` después de borrar (best-effort, con log; nunca bloquea ni deshace el borrado — App Store 5.1.1(v)).

**Colecciones**
- `GET /collections` → `{ items: [Collection] }` (`modules/backlog/shelves.ts` `getCollectionsWithMemberships`).
- `POST /collections` `{ name, vibe?, visibility }` → `200 Collection` (`modules/backlog/collections.ts` `createBacklog`; `visibility` default `profile`).
- `GET /collections/{id}` → `{ collection: Collection, titles: [Title], states: { titleId: TitleState } }` (`assertOwnsBacklog` + `getBacklogItemsWithState`; ajena o inexistente = mismo 404).
- `PATCH /collections/{id}` `{ name?, vibe?, visibility? }` → `Collection` (`updateBacklog`; `vibe: null | ""` la limpia).
- `DELETE /collections/{id}` → `204` (`deleteBacklog`; las membresías cascadean; **NO hace GC de `user_item`**, igual que la web: un título que solo vivía ahí conserva estado y reseña, huérfano de colección).
- `PUT /collections/{id}/titles/{titleId}` `{ externalRef?, paletteHex? }` (body opcional) → `{ title: Title, state: TitleState }` (`modules/backlog/membership.ts` `addTitleToBacklog` = `ensureUserItemAndMembership` + backfill de pre-order F3.8). Resuelve `titleId` como id de catálogo; **`externalRef` es solo respaldo** (`findCatalogItemByRef` por `(source, externalId)`; si no está cacheado → 404 "búscalo de nuevo": este handler nunca llama a un proveedor). **El `title.id` devuelto es el canónico** — la app lo adopta si difiere del que mandó.
- `DELETE /collections/{id}/titles/{titleId}` → `204` (`removeTitleFromBacklog`: si era la última membresía, borra `user_item` y la reseña; la app difiere el DELETE 5 s para el Deshacer, no hay undo en servidor).

**Títulos y estado propio**
- `GET /titles/{id}` → `{ title: Title (completo), state: TitleState | null, following: [{ handle, mark }], reviews: { items: [Review], nextCursor }, collections: [collectionId] }` (`getCatalogItem` + `getUserCatalogEntry` + `getItemReviewContext` + `getTitleStats` + `getItemDisplayMedia` + `getTitleActivityAmongFollowed`; mismas llamadas y orden que la ficha web). Id no-UUID (`parseId`) o desconocido = mismo 404. La reseña propia va primera con `hidden`. Álbum cuyo proveedor cayó y sin caché → `503 unavailable`.
- `GET /titles/{id}/reviews?cursor=` → `{ items: [Review], nextCursor }` (`modules/reviews/queries.ts` `getOthersReviewsPage`, la MISMA función que arma la primera página de `GET /titles/{id}`). Es la paginación de las reseñas de la ficha: la app toma `reviews.nextCursor` de `GET /titles/{id}` y lo sigue aquí. **Sin cursor = la misma primera página** que embebe la ficha (8 reseñas) sin la propia y con el mismo `nextCursor`; con cursor, páginas de 10 (el "ver más" de la web; keyset `(createdAt, id)`, mezclar tamaños es seguro). **La reseña propia no aparece en NINGUNA página**: vive fijada arriba en `GET /titles/{id}` (con `hidden`) y nunca se repite. Solo reseñas públicas (`isPublic AND username AND hidden_at IS NULL` dentro de la query): ningún ítem lleva `hidden` y `authorHandle` siempre es un handle. Cursor corrupto → `400 invalid` + `fields.cursor` (aquí además la mitad de id tiene que ser un UUID: es un `item_review.id`); cursor bien formado más allá del final → `{ items: [], nextCursor: null }`; id malformado o desconocido → el mismo 404 que `GET /titles/{id}`.
- `GET /titles?ids=a,b,c` (≤ 50) → `{ items: [Title] }` (`getCatalogItems`; ids desconocidos se omiten; conserva el orden pedido).
- `GET /me/titles` → `{ items: [{ titleId, state: TitleState }] }` (`modules/backlog/library.ts` `getUserLibrary`: toda la biblioteca, una entrada por `user_item`, `addedAt desc`).
- `PUT /me/titles/{id}/mark` `{ mark: "obsessed" | "liked" | "completed" | null, preview?: boolean }` → `TitleState` re-leído (`modules/backlog/state.ts` `setMark`). Semántica: cualquier marca implica `status='completed'`; `obsessed` = `obsessed=true` y **deja el veredicto intacto**; `liked` = `verdict='liked'`, `obsessed=false`; `completed` = completo sin veredicto ni obsesión; `null` = vuelve a `on_my_radar` y limpia ambos. **Solo re-estampa timestamps si el valor cambia** (un PUT repetido no mueve `obsessedAt` ni `statusChangedAt`). **Regla de estreno en servidor**: `releaseDate > now` sin `preview: true` → `409 conflict` + `reason: "not_released"` (en la web solo vivía en la UI). **Marcar sin guardar (fase 4b, decisión del founder)**: una marca no-`null` sobre un título del catálogo que NO está en tu biblioteca **crea** su estado (`user_item` sin membresía en ninguna colección) y responde `200` con el `TitleState` (`savedAt` = ese instante, `mark` la pedida); a partir de ahí aparece en `GET /me/titles` y en perfil/recap, pero en ninguna `Collection`. La app ofrece "guardar en" después (`PUT /collections/{id}/titles/{titleId}` le agrega membresía sin tocar el estado). Orden: id desconocido en el catálogo (o no-UUID) → `404`; la regla de estreno corre **antes** de crear (un `409` no deja nada); `mark: null` sobre un título sin estado → **`404`** (quitar la marca de algo que no está en la biblioteca no crea nada). `DELETE /me/titles/{id}` lo quita como a cualquier otro.
- `PUT /me/titles/{id}/review` `{ body, hasSpoiler }` → `Review` (`assertOwnsUserItem` + `modules/reviews/write.ts` `saveReview`: exige reacción previa → `409` + `reason: "reaction_required"`; enlaces → 400; 1..280 → 400; álbum nunca lleva spoiler; editar conserva `hiddenAt`). `DELETE` → `204` (idempotente).
- `DELETE /me/titles/{id}` → `204` (`removeTitleFromLibrary`: todas las membresías + estado + reseña; idempotente).
- `PUT|DELETE /me/titles/{id}/episodes/{key}` → `501 unsupported` (sin modelo; la app lo guarda local). Con bearer a propósito: sin token sigue siendo 401.

**Reportar y bloquear (App Store 1.2 · contenido generado por usuarios, 2026-09-24)**

Bloquear es **mutuo en visibilidad**: si hay un bloqueo en CUALQUIER dirección entre tú y otra persona, desaparece para ti (y tú para ella) de `GET /feed`, `GET /feed/suggestion`, las reseñas de `GET /titles/{id}` y `GET /titles/{id}/reviews`, `following` de `GET /titles/{id}`, `trending` de `GET /discover`, `GET /people/search`, `GET /people/suggestions`, `GET /me/onboarding/people`, `common` de `GET /people/{handle}` y tus `GET /me/following` · `GET /me/followers` (gate `notBlockedWith` dentro de cada query, `modules/social/block-gate.ts`). Bloquear borra los follows en **ambas** direcciones y nadie puede volver a seguir mientras exista. Reportar NO depende de bloqueos (puedes reportar a quien bloqueaste o a quien te bloqueó). La web (páginas públicas anónimas) no tiene bloqueos: sin sesión no hay a quién aplicarlos.

- `POST /people/{handle}/report` `{ reason: "spam" | "impersonation" | "harassment" | "illegal_content" | "other", details?: string (≤ 500, se recorta) }` → **`204` siempre** (`modules/reports/write.ts` `reportProfile`, el mismo código que `submitReportAction` de la web). Nunca confirma si el handle existe: inexistente, privado, **malformado** y **tú mismo** = `204` que no inserta nada. Lo único que no es 204 es un **body inválido** → `400 invalid` + `fields` (`fields.reason`, `fields.details`), validado ANTES de mirar el handle, así que no varía con él.
- `POST /reviews/{reviewId}/report` `{ reason: "unmarked_spoiler" | "spam" | "harassment" | "hate" | "illegal_content" | "off_topic" | "other" }` → **`204` siempre** (`reportReview`, el mismo código que `reportReviewAction`; los motivos son `REVIEW_REPORT_REASONS` de `modules/reviews/types.ts` — `impersonation` no aplica a una reseña → 400). `{reviewId}` = `Review.id`. Reseña inexistente, **propia**, **ya reportada por ti** o id no-UUID = `204` sin insertar. Body inválido → `400 invalid` + `fields.reason`.
- `PUT /me/blocks/{handle}` → `204` (`modules/social/block.ts` `blockUser`). Cualquier cuenta existente, pública **o privada**. Inexistente, **malformado** y **tu propio handle** = el mismo 404 (mismo cuerpo que `PUT /me/following`). Idempotente. En la misma transacción borra los follows en ambas direcciones.
- `DELETE /me/blocks/{handle | id}` → `204` idempotente (`unblockUser`). Acepta el **handle** o el **`id`** de `GET /me/blocks` (necesario cuando la fila trae `handle: null`). Handle desconocido, id desconocido o "no estaba bloqueado" = `204`. Solo algo que no es ni UUID ni un handle posible → el mismo 404 que `PUT`. Desbloquear **no** restaura follows.
- `GET /me/blocks` → `{ items: [BlockedPerson] }` (`listBlocked`; más reciente primero; sin paginar). Ejemplo: `{ "items": [ { "id": "3f2c…", "handle": "ana", "name": "Ana", "avatarUrl": "/api/avatar/ab12…" }, { "id": "9e1d…", "handle": null, "name": "Perfil privado", "avatarUrl": null } ] }`.

**Recap**
- `GET /recap/months` → `{ items: [{ era: "2026-08", label: "agosto 2026" }] }` (`modules/backlog/recap.ts` `getRecapMonths`, `recap-format.ts` `monthYear`).
- `GET /recap/{era}` → `{ era, label, stats: { completed, obsessions, reviews, saved }, top: Title | null, also: [Title] }` (`getRecapMonth` + `pickTop`/`alsoInMonth`; `era` = `YYYY-MM`; formato inválido o mes sin actividad = mismo 404). La tarjeta exportable sigue en la web (`/recap/tarjeta`): la app comparte el link; el intercambio bearer → cookie (`POST /auth/web-session`) es fase 4.

**Notificaciones y dispositivos** — ver §2.4. `GET /me/notifications` no existe (sin modelo de bandeja).

## 5. Lo implementado en iOS (fase 3)

- **`LiveAPI: KuraAPI`** (`ios/Kura/Services/LiveAPI.swift`): `Endpoint` + `APIClient` sobre `URLSession`, bearer en cada request, `KuraJSON.decoder` (ISO 8601 con y sin fracción), mapeo `error.code` + `reason` → `KuraAPIError` (`.unauthorized`, `.forbidden(code:)`, `.notFound`, `.invalid(fields:message:)`, `.conflict(code:message:)`, `.rateLimited(retryAfter:)`, `.unsupported`, `.unavailable`, `.offline`, `.server`). Reintento con backoff 0.5 / 1 / 2 s **solo en GET**. Es el `KuraAPI` por defecto (`KuraApp.init`).
- **`MockAPI`** (`Services/KuraAPI.swift`, mismo protocolo, sirve `MockData`) solo en DEBUG con `-kuraMock` o `-kuraScreen <nombre>` (`App/DebugLaunch.swift` → `KuraRuntime.usesMock`).
- **Token en Keychain** (`Services/Keychain.swift`, service `com.tromwey.kura`, account `bearer`; nunca `UserDefaults`). `Services/Session.swift` lee `exp` del JWT sin verificar firma; `AppStore.finishSplash` hace `POST auth/refresh` si faltan < 7 días. **Cualquier 401** borra el token, postea `.kuraSessionExpired` y el store vuelve a la entrada con aviso.
- **Base URL** = `KuraAPIBase` en `Info.plist`, armada desde **`KURA_API_SCHEME` + `KURA_API_HOST`** por configuración en `ios/project.yml` (Debug `http://localhost:3010/api/v1` · Release `https://baclog.app/api/v1`). Debug usa **`Kura/Info-Debug.plist`** (= `Info.plist` + `NSAppTransportSecurity › NSAllowsLocalNetworking`; hay que mantenerlo en sincronía a mano).
- **`AppStore`** por recursos: arranque = `GET /me` + `/collections` + `/me/titles` + `/me/following`, luego `GET /titles?ids=` para lo que falte; ficha, colección, feed, descubrir, persona, listas y recap cargan al entrar (`load*`). Membresías por `PUT/DELETE collections/{id}/titles/{titleId}` con Deshacer diferido 5 s (`deferRemove`); colecciones creadas optimistas con id temporal resuelto antes de cualquier escritura dependiente; `setMark(preview:)` revierte en `409 not_released`.
- **`LocalPrefs`** (`Services/LocalPrefs.swift`, UserDefaults, apagado en mock, se borra al cerrar sesión): todo lo `unsupported` (fijar, portada, orden manual, vista, episodios, recientes, silenciados).
- **Onboarding real** (`Features/Onboarding`): correo → código (`.oneTimeCode`) → `UsernameView` (handle con `GET /me/username/check` debounced, nombre y **año de nacimiento** — campo que el frame O1b no tenía; `403 underage` → `UnderageView` que cierra sesión) → `PickThreeView` (`GET /onboarding/pool?page=1`, `POST /me/onboarding/picks`) → `YourPeopleView` (`GET /me/onboarding/people`).
- **Fase 4b**: "Compartir" en la tarjeta del recap (`RecapShareView`) ya no comparte un link pelado. Llama a `POST auth/web-session` con `to = /recap/tarjeta?mes=<era>` y abre la URL en un `SFSafariViewController` (`SafariView`, pantalla completa). Si falla, muestra un toast con reintento manual.
- Pendiente en iOS: pintar `avatarUrl` (hoy sello por iniciales), navegar a `GET /people/{handle}/collections/{id}`, paginar reseñas en la ficha (el servidor ya sirve `GET /titles/{id}/reviews?cursor=`, fase 4a).
