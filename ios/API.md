# Kura · API `/api/v1` para la app iOS — contrato vigente

> Estado: **implementado — fases 0–3 en `main`** (2026-09-24, commits `14f1e2f` y `20ca848`). **Fase 4 pendiente** de decisiones del founder (§6, §7). Este archivo describe lo que el servidor HACE hoy; los zod de `src/app/api/v1/_lib/schemas.ts` son la forma exacta de cada payload y `scripts/api-smoke.ts` la valida contra un servidor vivo. ## 0. Contexto y principios

- La app web (Next 16, `src/`) habla con el servidor por **server actions**. La app iOS (`ios/`, SwiftUI) habla con **la misma app desplegada** por HTTP: `src/app/api/v1/**` es la API, `ios/Kura/Services/LiveAPI.swift` el cliente. Un solo deploy, una sola base.
- **Misma verdad, mismo código.** Cada handler reutiliza `src/modules/**`; **ninguno llama a una server action** (redirigen, revalidan rutas y asumen cookies). Toda regla que la web tenía dentro de una action se extrajo a un módulo y la action pasó a ser un wrapper fino (`assert*` → módulo con `userId` explícito → `revalidatePath`/`redirect`). Regla desde ahora: **una regla nueva va al módulo, nunca a la action**, porque la API la reutiliza.
- **Autorización 100 % app-layer, igual que la web** (`AGENTS.md`): el usuario sale del bearer y solo del bearer (`requireApiUser` → `apiContext`); ningún handler acepta `userId` en body, query ni path; propiedad re-checada por mutación (`assertOwnsBacklog`, `assertOwnsUserItem` funcionan bajo bearer gracias a `AsyncLocalStorage`); lecturas cross-user solo por los módulos ya gateados (`public.ts`, `social/*`, `reviews/*`). La API **no abrió ninguna excepción nueva de authz**.
- **Sin migraciones.** Lo que el modelo no tiene (fijar, orden manual, portada elegida, visibilidad "seguidores", episodios vistos, notificaciones, solicitudes) queda fuera del contrato o responde `unsupported`; la app lo guarda local (`LocalPrefs`). Migrar la base Neon compartida (local = beta = prod) requiere confirmación del founder.
- El dominio sigue siendo `baclog.app`; la API vive en `https://baclog.app/api/v1`. La API es **aditiva**: desplegarla no toca la web.

## 1. Convenciones

- **Base** `/api/v1`. JSON UTF-8, claves **camelCase**, ids como string (UUID de la base; las personas se identifican por `handle`, nunca por id). Fechas **ISO 8601 UTC sin fracción de segundo** (`"2026-09-24T15:00:00Z"`, `isoDate()` en `schemas.ts`): el `JSONDecoder.iso8601` de Swift rechaza `.000Z`.
- **Errores**: `{ "error": { "code", "message", "reason"?, "fields"?, "retryAfterSeconds"? } }`.
  - `code` fijo: `unauthorized` 401 · `forbidden` 403 · `not_found` 404 · `invalid` 400 · `conflict` 409 · `rate_limited` 429 · `unsupported` 501 · `unavailable` 503 · `internal` 500.
  - `reason` = **sub-código opcional** sobre el que la app ramifica: `underage` (bajo `forbidden`), `not_released` y `reaction_required` (bajo `conflict`), `taken` (bajo `conflict`, username).
  - `fields` solo en `invalid`: `campo → mensaje`, **en español**, listo para pintar bajo el campo (viene de `ZodError` o del handler).
  - `message` es texto final en la voz Kura (qué pasó y qué hacer; sin guiño). Todo 401 es el MISMO cuerpo, falle lo que falle (sin header, firma, `aud`, `exp`, usuario borrado, menor): un 401 distinguible es un oráculo.
  - Headers: **`X-Request-Id`** en toda respuesta v1 (para correlacionar un reporte de la app con el log); **`Retry-After`** (segundos) en todo 429.
- **Paginación** keyset: `?cursor=<opaco>` → `{ items, nextCursor: string | null }`. Cursor **ausente** = página 1; cursor **corrupto** (no decodifica) = `400 invalid` con `fields.cursor` — re-servir la página 1 en silencio escondería un bug del cliente como una primera página infinita. **No hay `limit`**: el tamaño de página lo fija el módulo (`FEED_EVENT_CHUNK` en el feed, la página de `getPeoplePage` en las listas de gente).
- **Envelopes**: **toda lista va en `{ items }`**, nunca un array desnudo. Las que paginan suman `nextCursor`; `me/following` y `me/followers` suman además `privateCount`. Ningún endpoint devuelve `null` a secas: lo opcional va envuelto (`{ event: FeedEvent | null }`).
- **Idempotencia** por clave natural: `PUT` = "poner en estado X" (membresía, marca, follow, reseña), `DELETE` = quitar; repetir no falla (un `DELETE` de algo que no existe es 204). Las escrituras devuelven el recurso resultante re-leído, no `{ ok }`. **Todos los `POST` que crean responden 200 con el recurso** (no 201).
- **Caché**: `Cache-Control: private, no-store` en toda respuesta v1 (éxito o error). Portadas: URLs de TMDB/mzstatic tal cual (ADR-007, hotlink); la app las carga con `AsyncImage`.
- **Versionado**: cambios incompatibles = `/api/v2`. Campos nuevos opcionales no rompen: los `Decodable` del iOS usan `decodeIfPresent` en todo lo opcional e ignoran claves desconocidas.
- **Rate limit**: 60 escrituras / 300 lecturas por minuto por usuario (`sub`), ventana deslizante **en memoria por instancia** (no global entre instancias de Vercel, no sobrevive un cold start; frena a un cliente desbocado, no es frontera de seguridad). `auth/*` limita por IP. Se evalúa **antes de leer la base** (la firma del token se verifica en CPU; la relectura del usuario viene después). Respuesta: 429 + `retryAfterSeconds` + `Retry-After`.
- **Runtime**: los handlers corren en Node (usan `node:async_hooks`), nunca en edge.

## 2. Autenticación

El web usa Auth.js v5 con JWT en cookie y el provider Credentials `otp` (`src/auth/config.ts`). Para móvil no hay cookies: se emite un **bearer propio** con las mismas garantías, sin tabla de sesiones.

### 2.1 Flujo OTP (implementado)

1. `POST /auth/otp/request` `{ email }` → `204`. Reusa `issueOtp` (`src/auth/otp.ts`; un código vivo por correo, cooldown de 60 s en DB). Cooldown → `429 rate_limited` con `retryAfterSeconds: 60`. 204 exista o no la cuenta (verify la crea; no hay nada que enumerar). Público, rate limit por IP (`withPublicApi`).
2. `POST /auth/otp/verify` `{ email, code, device: { platform: "ios", name, appVersion } }` → `{ token, user: Me }`. Reusa `verifyOtp` (crea el usuario si no existe, quema intentos, mata el código a los 5). Código malo/vencido → 401 (uno solo, nunca cuál). Cuenta menor → `403 forbidden` + `reason: "underage"`. `device` se valida y se loguea; no hay tabla de dispositivos (fase 4). El `token` es un **JWS HS256 firmado con `AUTH_SECRET`**, `sub = user.id`, `aud = "kura-ios"`, `iat`, `exp = +30 días`, `jti` aleatorio (`issueMobileToken`, `src/authz/api.ts`). Distinto del JWE de Auth.js: la cookie no vale como bearer ni al revés.
3. `POST /auth/refresh` (bearer) → `{ token, user: Me }`. **Solo rota cuando faltan < 7 días** para `exp`; si falta más, devuelve el **mismo** token que recibió. La app lo llama al abrir (`AppStore.finishSplash`).
4. `POST /auth/logout` (bearer) → `204`. **No revoca nada** (no hay estado que borrar): la app olvida el token. Deuda registrada: `users.token_version` (fase 4, migración) para invalidar todos los bearers de una cuenta; hoy un bearer robado **no es revocable** salvo borrando la cuenta o rotando `AUTH_SECRET` (que expulsa a todos).

`requireApiUser(request)` (`src/authz/api.ts`): lee `Authorization: Bearer`, verifica firma/alg/aud/exp, **relee `users` por `sub` en cada request** con `loadUserById` (`src/auth/session.ts`, la misma lista de campos que la cookie, nunca `birthYear`) y devuelve el mismo `CurrentUser` que `requireUser()`. Cuenta borrada o `isMinor` → 401 aunque la firma sea válida (la revocación es la relectura). `withApi` envuelve **todo** handler v1: `requireBearer` (401 sin DB) → rate limit por `sub` → `loadUserById` (401 si la fila no está o es menor) → `apiContext.run({ user }, handler)` → errores al contrato (con `rid`, método y ruta en el log) → `no-store` + `X-Request-Id`. `getCurrentUser()` consulta `apiContext` **antes** de `auth()`, así que dentro de un request v1 jamás se lee la cookie y `assertUser`/`assertOwnsBacklog`/`assertOwnsUserItem` funcionan sin cambios. `GET /me` pasa por `assertUser()` a propósito para que el puente se ejercite en cada smoke.

`readApiUser(request)` es el gemelo suave para rutas **fuera** de v1 que sirven web y app: hoy solo `/api/avatar/[key]`, que acepta **bearer además de cookie** (la app carga su propia foto sin cookie; mismo gate, mismo 404).

### 2.2 Sign in with Apple / Google (fase 4)

La tabla `account` (adapter de Auth.js) existe pero está vacía para OTP. `POST /auth/apple` `{ identityToken, authorizationCode, fullName? }` verificaría el JWT de Apple (`aud` = bundle `io.communeo.kura`), buscaría `account(provider='apple', providerAccountId=sub)`, enlazaría por correo verificado o crearía el usuario, y devolvería el mismo `{ token, user }`. **Fuera de la entrega actual**; la app lanza solo con correo (Apple exige "Sign in with Apple" solo si ofreces otro login social de terceros). Los botones de Apple/Google en O1 avisan que llegan después.

## 4. Endpoints

Todos bajo `/api/v1`, todos con bearer salvo `auth/otp/*`. Entre paréntesis, el módulo que se reutiliza.

**Auth** — ver §2.1.

**Cuenta**
- `GET /me` → `Me` (`assertUser` + `_lib/me.ts`).
- `PATCH /me` `{ name?, preferredService?, notifyReleases?, isPublic? }` → `Me` re-leído (`modules/account/profile.ts` `updateProfile`, misma validación que las cuatro actions; campo ausente = intacto; body vacío = no-op que devuelve `Me`).
- `GET /me/username/check?u=` → `{ status: "free" | "taken" | "invalid" }` (`modules/account/username.ts` `checkUsername`; lo malformado o reservado es `invalid`, no 400 — el campo se escribe en vivo; el propio handle actual lee `free`).
- `PUT /me/username` `{ username }` → `Me` (`claimUsername`; F2.17: reclamar pone `isPublic = true`). 400 `invalid` + `fields.username` si nunca podrá reclamarse (forma o `RESERVED`); `409 conflict` + `reason: "taken"` si alguien lo tiene.
- `POST /me/onboarding` `{ name, birthYear }` → `Me` (`modules/account/onboarding.ts` `completeOnboarding`; F2.2). Menor de 13 → la cuenta queda bloqueada (este bearer y todo login futuro son 401) y responde `403 forbidden` + `reason: "underage"`.
- `POST /me/onboarding/picks` `{ titles: [{ id?, externalRef?, paletteHex? }] }` (1..3) → `{ collection: Collection }` (`modules/backlog/picks.ts` `completePicks`: "Obsesiones" o la colección más reciente en re-entrada; todos los títulos se resuelven ANTES de escribir; uno no cacheado → 404 sin escribir nada).
- `GET /me/onboarding/people` → `{ items: [Person] }` (`modules/social/people.ts`; sin picks → `items: []`; `why` = "Le obsesiona {título}").
- `PUT /me/avatar` → `Me` con el `avatarUrl` nuevo. Acepta **multipart/form-data con parte `file`** o **body raw con `Content-Type: image/webp | image/jpeg | image/png`**, **≤ 400 KB** (`AVATAR_MAX_BYTES`); el servidor sniffea magic bytes (`modules/avatar/write.ts` `storeAvatar`, SVG jamás). `DELETE /me/avatar` → `Me` con `avatarUrl: null` (idempotente).
- `DELETE /me` → `204` (`modules/account/delete.ts`; cascadea todo; el bearer queda revocado en la siguiente relectura — la app olvida el token).

**Colecciones**
- `GET /collections` → `{ items: [Collection] }` (`modules/backlog/shelves.ts` `getCollectionsWithMemberships`).
- `POST /collections` `{ name, vibe?, visibility }` → `200 Collection` (`modules/backlog/collections.ts` `createBacklog`; `visibility` default `profile`).
- `GET /collections/{id}` → `{ collection: Collection, titles: [Title], states: { titleId: TitleState } }` (`assertOwnsBacklog` + `getBacklogItemsWithState`; ajena o inexistente = mismo 404).
- `PATCH /collections/{id}` `{ name?, vibe?, visibility? }` → `Collection` (`updateBacklog`; `vibe: null | ""` la limpia).
- `DELETE /collections/{id}` → `204` (`deleteBacklog`; las membresías cascadean; **NO hace GC de `user_item`**, igual que la web: un título que solo vivía ahí conserva estado y reseña, huérfano de colección).
- `PUT /collections/{id}/titles/{titleId}` `{ externalRef?, paletteHex? }` (body opcional) → `{ title: Title, state: TitleState }` (`modules/backlog/membership.ts` `addTitleToBacklog` = `ensureUserItemAndMembership` + backfill de pre-order F3.8). Resuelve `titleId` como id de catálogo; **`externalRef` es solo respaldo** (`findCatalogItemByRef` por `(source, externalId)`; si no está cacheado → 404 "búscalo de nuevo": este handler nunca llama a un proveedor). **El `title.id` devuelto es el canónico** — la app lo adopta si difiere del que mandó.
- `DELETE /collections/{id}/titles/{titleId}` → `204` (`removeTitleFromBacklog`: si era la última membresía, borra `user_item` y la reseña; la app difiere el DELETE 5 s para el Deshacer, no hay undo en servidor).

**Títulos y estado propio**
- `GET /titles/{id}` → `{ title: Title (completo), state: TitleState | null, following: [{ handle, mark }], reviews: { items: [Review], nextCursor }, collections: [collectionId] }` (`getCatalogItem` + `getUserCatalogEntry` + `getItemReviewContext` + `getTitleStats` + `getItemDisplayMedia` + `getTitleActivityAmongFollowed`; mismas llamadas y orden que la ficha web). Id no-UUID (`parseId`) o desconocido = mismo 404. La reseña propia va primera con `hidden`. Álbum cuyo proveedor cayó y sin caché → `503 unavailable`.
- `GET /titles?ids=a,b,c` (≤ 50) → `{ items: [Title] }` (`getCatalogItems`; ids desconocidos se omiten; conserva el orden pedido).
- `GET /me/titles` → `{ items: [{ titleId, state: TitleState }] }` (`modules/backlog/library.ts` `getUserLibrary`: toda la biblioteca, una entrada por `user_item`, `addedAt desc`).
- `PUT /me/titles/{id}/mark` `{ mark: "obsessed" | "liked" | "completed" | null, preview?: boolean }` → `TitleState` re-leído (`modules/backlog/state.ts` `setMark`). Semántica: cualquier marca implica `status='completed'`; `obsessed` = `obsessed=true` y **deja el veredicto intacto**; `liked` = `verdict='liked'`, `obsessed=false`; `completed` = completo sin veredicto ni obsesión; `null` = vuelve a `on_my_radar` y limpia ambos. **Solo re-estampa timestamps si el valor cambia** (un PUT repetido no mueve `obsessedAt` ni `statusChangedAt`). **Regla de estreno en servidor**: `releaseDate > now` sin `preview: true` → `409 conflict` + `reason: "not_released"` (en la web solo vivía en la UI). Título fuera de la biblioteca → 404.
- `PUT /me/titles/{id}/review` `{ body, hasSpoiler }` → `Review` (`assertOwnsUserItem` + `modules/reviews/write.ts` `saveReview`: exige reacción previa → `409` + `reason: "reaction_required"`; enlaces → 400; 1..280 → 400; álbum nunca lleva spoiler; editar conserva `hiddenAt`). `DELETE` → `204` (idempotente).
- `DELETE /me/titles/{id}` → `204` (`removeTitleFromLibrary`: todas las membresías + estado + reseña; idempotente).
- `PUT|DELETE /me/titles/{id}/episodes/{key}` → `501 unsupported` (sin modelo; la app lo guarda local). Con bearer a propósito: sin token sigue siendo 401.

**Descubrir y búsqueda**
- `GET /search?q=&kind=all|film|series|album` → `{ items: [SearchResult] }` (`unifiedSearchDetailed`; TMDB + iTunes en paralelo, upsert en `catalog_item`). `503 unavailable` **solo** cuando todos los proveedores pedidos fallaron y no volvió nada; "sin resultados" honesto = 200 con `items: []`.
- `GET /discover` → `{ recommended: [{ title, reason, seedTitleId }], trending: [{ title, saves, people: [handle] }], upcoming: [{ title, releaseDate }] }` (`getObsessionRails` intercalados por `modules/recs/discover-cards.ts` `recCards` — solo recos YA cacheadas, nunca el motor; `getTrendingAmongFollowed`; `getLibraryUpcoming`).
- `GET /onboarding/pool?page=1..20` → `{ items: [Title], nextPage: number | null }` (`getOnboardingPoolPage`, el mismo pool curado que la web; grid "elige tres"; con bearer como la web lo tiene tras sesión). Proveedores caídos y sin caché → `503 unavailable`.

**Gente y feed**
- `GET /people/{handle}` → `Person` completo (`people/_lib/person.ts` `buildPerson`). **404 idéntico** para privado, inexistente y **malformado** (la gramática del handle se valida como 404, no 400: un 400 diría qué strings vale la pena probar). El dueño viéndose a sí mismo: `isFollowing: false`, `common: []`.
- `GET /people/{handle}/collections/{id}` → `{ collection, titles, states }` como `GET /collections/{id}` pero por `getPublicBacklog` (gate dueño público AND colección pública dentro de la query; `states` = estado del DUEÑO como la página pública lo muestra: `obsessed` siempre, veredicto solo si completó; `savedAt` = `backlog_item.addedAt`).
- `GET /people/suggestions` → `{ items: [Person] }` (`getFollowSuggestions`, 8; `why` = "N colecciones · actividad …").
- `GET /people/search?q=` → `{ items: [Person] }` (`searchProfiles`; `q` > 60 chars → 400; < 2 chars → `items: []`; solo públicos).
- `GET /me/following?cursor=` · `GET /me/followers?cursor=` → `{ items: [Person], nextCursor, privateCount }` (`getPeoplePage`; listas solo del dueño, conteos públicos; seguidores sin handle público se agregan en `privateCount`, nunca como identidad; un seguido que se volvió privado conserva su fila con `isPrivate: true`).
- `PUT /me/following/{handle}` → `204` (`modules/social/follow.ts` `followUser`; solo perfiles públicos; propio, privado, inexistente y **malformado** = mismo 404). `DELETE /me/following/{handle}` → `204` (`unfollowUser`; **no gatea en `isPublic`**, `AGENTS.md`; sin arista o desconocido = 204; malformado = 404).
- `GET /feed?cursor=` → `{ items: [FeedEvent], nextCursor }` (`getFeedEventsPage`: un chunk keyset de EVENTOS; nadie seguido → página vacía).
- `GET /feed/suggestion` → `{ event: FeedEvent(kind "suggest") | null }` (`getFeedSuggestion`).

**Recap**

## 5. Lo implementado en iOS (fase 3)

- **`LiveAPI: KuraAPI`** (`ios/Kura/Services/LiveAPI.swift`): `Endpoint` + `APIClient` sobre `URLSession`, bearer en cada request, `KuraJSON.decoder` (ISO 8601 con y sin fracción), mapeo `error.code` + `reason` → `KuraAPIError` (`.unauthorized`, `.forbidden(code:)`, `.notFound`, `.invalid(fields:message:)`, `.conflict(code:message:)`, `.rateLimited(retryAfter:)`, `.unsupported`, `.unavailable`, `.offline`, `.server`). Reintento con backoff 0.5 / 1 / 2 s **solo en GET**. Es el `KuraAPI` por defecto (`KuraApp.init`).
- **`MockAPI`** (`Services/KuraAPI.swift`, mismo protocolo, sirve `MockData`) solo en DEBUG con `-kuraMock` o `-kuraScreen <nombre>` (`App/DebugLaunch.swift` → `KuraRuntime.usesMock`).
- **Token en Keychain** (`Services/Keychain.swift`, service `io.communeo.kura`, account `bearer`; nunca `UserDefaults`). `Services/Session.swift` lee `exp` del JWT sin verificar firma; `AppStore.finishSplash` hace `POST auth/refresh` si faltan < 7 días. **Cualquier 401** borra el token, postea `.kuraSessionExpired` y el store vuelve a la entrada con aviso.
- **Base URL** = `KuraAPIBase` en `Info.plist`, armada desde **`KURA_API_SCHEME` + `KURA_API_HOST`** por configuración en `ios/project.yml` (Debug `http://localhost:3010/api/v1` · Release `https://baclog.app/api/v1`). Debug usa **`Kura/Info-Debug.plist`** (= `Info.plist` + `NSAppTransportSecurity › NSAllowsLocalNetworking`; hay que mantenerlo en sincronía a mano).
- **`AppStore`** por recursos: arranque = `GET /me` + `/collections` + `/me/titles` + `/me/following`, luego `GET /titles?ids=` para lo que falte; ficha, colección, feed, descubrir, persona, listas y recap cargan al entrar (`load*`). Membresías por `PUT/DELETE collections/{id}/titles/{titleId}` con Deshacer diferido 5 s (`deferRemove`); colecciones creadas optimistas con id temporal resuelto antes de cualquier escritura dependiente; `setMark(preview:)` revierte en `409 not_released`.
- **`LocalPrefs`** (`Services/LocalPrefs.swift`, UserDefaults, apagado en mock, se borra al cerrar sesión): todo lo `unsupported` (fijar, portada, orden manual, vista, episodios, recientes, silenciados).
- **Onboarding real** (`Features/Onboarding`): correo → código (`.oneTimeCode`) → `UsernameView` (handle con `GET /me/username/check` debounced, nombre y **año de nacimiento** — campo que el frame O1b no tenía; `403 underage` → `UnderageView` que cierra sesión) → `PickThreeView` (`GET /onboarding/pool?page=1`, `POST /me/onboarding/picks`) → `YourPeopleView` (`GET /me/onboarding/people`).
- Pendiente en iOS: pintar `avatarUrl` (hoy sello por iniciales), navegar a `GET /people/{handle}/collections/{id}`, paginar reseñas en la ficha.
