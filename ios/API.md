## 0. Contexto y principios

- La app web (Next 16, `src/`) habla con el servidor por **server actions**. La app iOS (`ios/`, SwiftUI) habla con **la misma app desplegada** por HTTP: `src/app/api/v1/**` es la API, `ios/Kura/Services/LiveAPI.swift` el cliente. Un solo deploy, una sola base.
- **Misma verdad, mismo código.** Cada handler reutiliza `src/modules/**`; **ninguno llama a una server action** (redirigen, revalidan rutas y asumen cookies). Toda regla que la web tenía dentro de una action se extrajo a un módulo y la action pasó a ser un wrapper fino (`assert*` → módulo con `userId` explícito → `revalidatePath`/`redirect`). Regla desde ahora: **una regla nueva va al módulo, nunca a la action**, porque la API la reutiliza.
- **Autorización 100 % app-layer, igual que la web** (`AGENTS.md`): el usuario sale del bearer y solo del bearer (`requireApiUser` → `apiContext`); ningún handler acepta `userId` en body, query ni path; propiedad re-checada por mutación (`assertOwnsBacklog`, `assertOwnsUserItem` funcionan bajo bearer gracias a `AsyncLocalStorage`); lecturas cross-user solo por los módulos ya gateados (`public.ts`, `social/*`, `reviews/*`). La API **no abrió ninguna excepción nueva de authz**.
- **Sin migraciones hasta la fase 4b** (la primera es `0027_user_token_version_notify_recap`, aplicada el 2026-09-24: `users.token_version` §2.1 y `users.notify_recap` §4). Después: `0028_user_block` (4c) y `0029_device_sessions_push` (4d/4e: `mobile_session`, `device_token`, `follow_push_notice`, `users.notify_followers`; aplicada el 2026-09-24). Lo que el modelo no tiene (fijar, orden manual, portada elegida, visibilidad "seguidores", episodios vistos, notificaciones, solicitudes) queda fuera del contrato o responde `unsupported`; la app lo guarda local (`LocalPrefs`). Migrar la base Neon compartida (local = beta = prod) requiere confirmación del founder.
- El dominio es `get-kura.app` (desde 2026-09-29; antes `baclog.app`, que sigue respondiendo `/api/*` para los builds ya instalados y redirige la web); la API vive en `https://get-kura.app/api/v1`. La API es **aditiva**: desplegarla no toca la web.

## 1. Convenciones

- **Base** `/api/v1`. JSON UTF-8, claves **camelCase**, ids como string (UUID de la base; las personas se identifican por `handle`, nunca por id). Fechas **ISO 8601 UTC sin fracción de segundo** (`"2026-09-24T15:00:00Z"`, `isoDate()` en `schemas.ts`): el `JSONDecoder.iso8601` de Swift rechaza `.000Z`.
- **Errores**: `{ "error": { "code", "message", "reason"?, "fields"?, "retryAfterSeconds"?, "mergeToken"?, "source"? } }` (`mergeToken`/`source` solo en el `409 linked_elsewhere` de §2.5).
  - `code` fijo: `unauthorized` 401 · `forbidden` 403 · `not_found` 404 · `invalid` 400 · `conflict` 409 · `rate_limited` 429 · `unsupported` 501 · `unavailable` 503 · `internal` 500.
  - **Única excepción de status (fase 4g)**: `invalid` + `reason: "invalid_proof"` sale con **HTTP 422**, no 400 — una prueba de propiedad rechazada (token de Apple/Google o código de fusión) en una ruta CON bearer (§2.5). No es 401 porque la app trata todo 401 como "sesión muerta" y cierra sesión; el 401 queda solo para un bearer ausente/inválido.
  - `reason` = **sub-código opcional** sobre el que la app ramifica: `underage` y `lists_private` (bajo `forbidden`; el segundo trae además `visibility`, ver `GET /people/{handle}/followers`), `not_released` y `reaction_required` (bajo `conflict`), `taken` (bajo `conflict`, username), `linked_elsewhere` · `provider_already_linked` · `merge_token_invalid` · `last_way_in` (bajo `conflict`, fase 4g) e `invalid_proof` (bajo `invalid`, HTTP 422, fase 4g). Además:
    - **`onboarding_required`** (bajo `forbidden`, 403; F2.2, 2026-10-01): la cuenta no terminó el onboarding (nombre **y** año de nacimiento, `Me.onboardingComplete: false`). Lo responden las escrituras sociales/UGC: `PATCH /me` con `name` o `isPublic: true`, `PUT /me/following/{handle}`, `PUT /me/titles/{id}/review`, `POST /people/{handle}/report`, `POST /reviews/{id}/report`, `POST /parties`, `PATCH /parties/{id}`, `POST /parties/{id}/invite`, `POST /invites/{token}/join`. Se decide SOLO sobre la fila del que llama y antes de mirar el recurso (no es oráculo). Qué hacer: mandar a la persona al onboarding (`POST /me/onboarding`) y reintentar.
    - **`cooldown`** · **`hourly_cap`** · **`ip_limit`** (bajo `rate_limited`, 429, siempre con `retryAfterSeconds` y `Retry-After`): `cooldown` = ya hay un código enviado hace < 60 s **y sigue sirviendo** (la única razón con la que la app puede decir "revisa tu correo"); `hourly_cap` = un tope por hora, o un cooldown sin código usable — no afirmar que hay código; `ip_limit` = el limitador por red de las rutas públicas (`auth/*`, `GET /invites/{token}`), no se miró ni se envió nada. `cooldown`/`hourly_cap` salen de `POST /auth/otp/request` (§2.1) y `POST /me/merge/otp/request` (§2.5). En las dos, `hourly_cap` con `retryAfterSeconds` ≤ 60 puede ser "el correo del último código no salió y el código se retiró" (ronda 5): espera y pide otro, sin "revisa tu correo". Un 429 **sin** `reason` en una ruta con bearer es el limitador por usuario (60 escrituras / 300 lecturas por minuto).
    - **`locked`** (bajo `unauthorized`, 401; 2026-10-01, ronda 4): solo en `POST /auth/otp/verify`. Ese código ya no puede servir aunque se teclee bien — gastó sus 5 intentos, o se agotó el presupuesto de intentos del correo (o el de la cuenta demo). `message` (copy unificado, ronda 7): **"Se intentó demasiadas veces. Pide otro código más tarde."** (antes: "Demasiados intentos con ese código. Pide uno nuevo." — se cambió porque `locked` agrupa tres causas y en dos de ellas pedir otro código de inmediato tampoco sirve). Qué hacer: pintar el `message` y ofrecer **pedir otro código más tarde**, no "revisa el código" ni "pide uno ya". Un 401 de esa ruta **sin** `reason` = código incorrecto o vencido (el de siempre). No depende de que exista una cuenta con ese correo (los topes son por correo + red). Una build que no conozca `locked` ve el 401 de siempre.
  - **`PUT /me/avatar` — sus 400** (todos `invalid`, con el mismo texto en `message` y en `fields.file`, listo para pintar): cuerpo que no es ni `multipart/form-data` ni `image/webp|jpeg|png`, o bytes cuyo magic number no es de esos tres (SVG incluido) → "La foto tiene que ser JPEG, PNG o WebP. Prueba con otra."; multipart ilegible → "El formulario no se pudo leer."; multipart sin parte `file` → "No llegó ninguna foto. Elige una y vuelve a intentarlo."; más de 400 KB (`AVATAR_MAX_BYTES`; también un `Content-Length` > 800 KB, sin leer el cuerpo) → "La foto pesa demasiado. Prueba con otra."; un cuerpo vacío cuenta como formato inválido (el primer mensaje). Nunca 413/415: siempre 400 + `fields.file`.
  - `fields` solo en `invalid`: `campo → mensaje`, **en español**, listo para pintar bajo el campo (viene de `ZodError` o del handler).
  - `message` es texto final en la voz Kura (qué pasó y qué hacer; sin guiño). Todo 401 es el MISMO cuerpo, falle lo que falle (sin header, firma, `aud`, `exp`, usuario borrado, menor): un 401 distinguible es un oráculo.
  - Headers: **`X-Request-Id`** en toda respuesta v1 (para correlacionar un reporte de la app con el log); **`Retry-After`** (segundos) en todo 429.
- **Paginación** keyset: `?cursor=<opaco>` → `{ items, nextCursor: string | null }`. Cursor **ausente** = página 1; cursor **corrupto** (no decodifica: la mitad de instante tiene que ser exactamente lo que emite el servidor, ISO 8601 UTC `YYYY-MM-DDTHH:MM:SS(.sss)Z` con año ≥ 2000) = `400 invalid` con `fields.cursor` — re-servir la página 1 en silencio escondería un bug del cliente como una primera página infinita. **No hay `limit`**: el tamaño de página lo fija el módulo (`FEED_EVENT_CHUNK` en el feed, la página de `getPeoplePage` en las listas de gente, `REVIEW_PAGE_SIZE`/`REVIEW_MORE_SIZE` en las reseñas de un título).
- **Envelopes**: **toda lista va en `{ items }`**, nunca un array desnudo. Las que paginan suman `nextCursor`; `me/following` y `me/followers` suman además `privateCount`; `people/{handle}/followers` y `people/{handle}/following` suman `anonymousCount`. Ningún endpoint devuelve `null` a secas: lo opcional va envuelto (`{ event: FeedEvent | null }`).
- **Idempotencia** por clave natural: `PUT` = "poner en estado X" (membresía, marca, follow, reseña), `DELETE` = quitar; repetir no falla (un `DELETE` de algo que no existe es 204). Las escrituras devuelven el recurso resultante re-leído, no `{ ok }`. **Todos los `POST` que crean responden 200 con el recurso** (no 201).
- **Caché**: `Cache-Control: private, no-store` en toda respuesta v1 (éxito o error). Portadas: URLs de TMDB/mzstatic tal cual (ADR-007, hotlink); la app las carga con `AsyncImage`.
- **Versionado**: cambios incompatibles = `/api/v2`. Campos nuevos opcionales no rompen: los `Decodable` del iOS usan `decodeIfPresent` en todo lo opcional e ignoran claves desconocidas.
- **Rate limit**: 60 escrituras / 300 lecturas por minuto por usuario (`sub`), ventana deslizante **en memoria por instancia** (no global entre instancias de Vercel, no sobrevive un cold start; frena a un cliente desbocado, no es frontera de seguridad). `auth/*` limita por IP. Se evalúa **antes de leer la base** (la firma del token se verifica en CPU; la relectura del usuario viene después). Respuesta: 429 + `retryAfterSeconds` + `Retry-After`.
- **Runtime**: los handlers corren en Node (usan `node:async_hooks`), nunca en edge.

## 2. Autenticación

El web usa Auth.js v5 con JWT en cookie y el provider Credentials `otp` (`src/auth/config.ts`). Para móvil no hay cookies: se emite un **bearer propio** con las mismas garantías, ligado desde la fase 4d a una fila de `mobile_session` por instalación (§2.3). Tres formas de entrar, todas con la MISMA respuesta `{ token, user: Me }`: código por correo (§2.1), Apple y Google (§2.2).

### 2.1 Flujo OTP (implementado)

1. `POST /auth/otp/request` `{ email }` → `204`. Reusa `issueOtp` (`src/auth/otp.ts`). 204 exista o no la cuenta (verify la crea; no hay nada que enumerar). **Desde 2026-10-01 (ciclo 3) el correo sale DESPUÉS de responder**: el 204 significa "código armado", no "correo entregado" — si el envío falla, el código se retira **y esa emisión se devuelve** (2026-10-01, ronda 4: ya no gasta ninguno de los 5 por hora): durante el minuto siguiente `otp/request` responde 429 `hourly_cap` con `retryAfterSeconds` ≤ 60 (no hay código que buscar), y pasado ese minuto emite normalmente (ya no hay un 500 por fallo del mailer). Los cubos por IP (`ip_limit`) se llavean por red: IPv4 tal cual, IPv6 por /64. Público, rate limit por IP (`withPublicApi`). **429 `rate_limited`** siempre con `reason`, `retryAfterSeconds` (la espera real) y cabecera `Retry-After`:
   - `reason: "cooldown"` — ya te enviamos un código hace menos de 60 s y sigue sirviendo (`retryAfterSeconds` ≤ 60). **Es la ÚNICA razón con la que la app puede decir "revisa tu correo".**
   - `reason: "hourly_cap"` — tope (5 códigos/hora desde tu red, 15/hora para ese correo entre todos) o un cooldown sin código usable (el correo falló o se gastaron los intentos). `retryAfterSeconds` puede llegar a 3600. **No afirmar que hay un código.**
   - `reason: "ip_limit"` — el limitador por IP: no se envió nada (`retryAfterSeconds` ≤ 60). En ESTA ruta el `message` es el propio (copy A6): «Demasiados intentos desde esta red. Podrás pedir un código en {tiempo}.»; en el resto de rutas públicas es el genérico de `rate_limited`. Lo lleva TODO 429 del limitador de las rutas públicas (`auth/*`, `invites/{token}`).
   - Regla de cliente: `reason == "cooldown"` ⇒ el código sigue sirviendo; cualquier otro ⇒ no afirmar que hay código; sin `reason` (servidor viejo) y `retryAfterSeconds ≤ 60` ⇒ tratar como cooldown.
   - Ejemplo: `{ "error": { "code": "rate_limited", "message": "Ya te enviamos un código hace poco y sigue siendo válido. Revisa tu correo o espera 42 s para pedir otro.", "reason": "cooldown", "retryAfterSeconds": 42 } }`.
   - Los presupuestos son por (correo, red del que pide): que OTRA persona pida códigos o falle intentos para tu correo no gasta los tuyos (`state/security.md`). `POST /auth/otp/verify`: 5 intentos por código desde la red que lo pidió; si tu IP cambió entre pedir y teclear, el código sigue valiendo (cuenta contra 10 intentos "ajenos" por hora del correo).
2. `POST /auth/otp/verify` `{ email, code, device: { platform: "ios", name, appVersion } }` → `{ token, user: Me }`. Reusa `verifyOtp` (crea el usuario si no existe, quema intentos, mata el código a los 5). Código malo/vencido → 401 (uno solo, nunca cuál). **Código bloqueado por intentos → el mismo 401 con `reason: "locked"`** y su propio `message` ("Se intentó demasiadas veces. Pide otro código más tarde.", ver §1): la app pinta ese mensaje (esperar y pedir otro); sin `reason` = incorrecto o vencido. Cuenta menor → `403 forbidden` + `reason: "underage"`. `device` (`platform: "ios"`, `name` 1..120, `appVersion` 1..40) se guarda como la sesión de esta instalación (§2.3) y el bearer lleva su id como `sid`; el log estructurado lleva plataforma, versión, usuario y `sessionId`, nunca `device.name` (texto libre = PII). El `token` es un **JWS HS256 firmado con `AUTH_SECRET`**, `sub = user.id`, `aud = "kura-ios"`, `iat`, `exp = +30 días`, `jti` aleatorio (`issueMobileToken`, `src/authz/api.ts`). Distinto del JWE de Auth.js: la cookie no vale como bearer ni al revés.
3. `POST /auth/refresh` (bearer) `{ device? }` (body **opcional**: sin body, `{}` o `{ device }`) → `{ token, user: Me }`. **Solo rota cuando faltan < 7 días** para `exp`; si falta más, devuelve el **mismo** token que recibió. El token nuevo se acuña con el `tv` vigente y **el mismo `sid`**. Si llega `device` y el bearer tiene `sid`, actualiza nombre/versión de esa sesión (la app debería mandarlo al abrir: así una actualización de la app se ve en `GET /me/sessions`). **Token legado sin `sid`** (acuñado antes de 4d) con la migración 0029 viva: se le **crea sesión** (con `device` del body, o `platform "ios"`, `deviceName "iPhone"`, `appVersion "desconocida"` sin body) y se devuelve **siempre un token nuevo** con ese `sid`, falte lo que falte para `exp` — la app debe guardar el token que vuelve. Un refresh no revoca el viejo (muere en su `exp`, con el próximo logout de la cuenta o al revocar su sesión; un legado sin `sid` sigue vivo hasta su `exp`). La app lo llama al abrir (`AppStore.finishSplash`).
4. `POST /auth/logout` (bearer) → `204`. **"Cerrar sesión en todos lados"** (fase 4b, decisión del founder): incrementa `users.token_version` en una sola sentencia atómica (`token_version + 1`). Desde ese instante **todos** los bearers de la cuenta, de cualquier dispositivo, todo handoff web pendiente **y toda cookie web de Auth.js de la cuenta** (incluida la que abrió un handoff en el `SFSafariViewController`, y la de cualquier navegador donde se haya entrado con código) dan lo mismo que "sin sesión": 401 en v1, redirect a `/login` en la web. La cookie lleva su propio `tv` (lo pone `authorize`, lo copia el callback `jwt`) y `getCurrentUser` (`src/auth/session.ts`) lo compara con `token_version` en la MISMA relectura de la fila que ya hacía; una cookie de antes de 4b no trae `tv` y cuenta como 0. Es a nivel **cuenta** (decisión del founder, se mantiene tras 4d): además de subir `token_version`, marca **todas** las sesiones de `mobile_session` como revocadas y borra **todos** los `device_token` de la cuenta, en una sola transacción (`logoutEverywhere`, `src/auth/mobile-sessions.ts`) — ningún iPhone sigue recibiendo push de una cuenta de la que salió. Para sacar UN dispositivo está `DELETE /me/sessions/{id}` (§2.3). El "cerrar sesión" de la web solo borra la cookie de ese navegador (no incrementa la versión). Llamarlo con el token que acaba de revocar es 401; con un token nuevo vuelve a incrementar (mismo efecto). Activo desde el 2026-09-24 (migración 0027 aplicada, `TOKEN_VERSION_LIVE = true` en `src/auth/user-row.ts`; la constante queda como kill-switch documentado: en `false` logout vuelve a ser el no-op de antes y todo `tv` se compara contra 0).
5. `POST /auth/web-session` (bearer) `{ to? }` → `{ url }` (fase 4b). Devuelve una URL **absoluta, de un solo uso, que vive 60 s**, `<origen>/api/auth/handoff?t=<jws>&to=<path>`. Abierta en un `SFSafariViewController`, deja la web **ya autenticada** (cookie de Auth.js) y redirige a `to`. Sirve para las pantallas que solo existen en web; hoy es la tarjeta del recap (`/recap/tarjeta`, el exportador). `to` es opcional (por defecto `/recap/tarjeta`) y tiene que salir de una **lista blanca**: `/recap/tarjeta` y `/recap`, los dos con `?mes=YYYY-MM` opcional (`/` salió de la lista en 4b: la app no lo usa y cada destino extra amplía lo que puede hacer un handoff plantado). Cualquier otra cosa (URL absoluta, `//host`, `\`, otro path u otro param) → `400 invalid` + `fields.to`; nunca se "limpia" en silencio. Rate limit de escritura normal. **La URL no se comparte**: es una credencial de un uso. La app la abre directo, y `SFSafariViewController` tiene su propio cookie jar, no el de Safari.

**Bearer**: JWS HS256 (`AUTH_SECRET`) con `sub`, `aud = "kura-ios"`, **`tv`** (= `users.token_version` al acuñar), **`sid`** (= `mobile_session.id`, fase 4d), `iat`, `exp = +30 días` y `jti`. Lo acuñan `otp/verify`, `auth/apple`, `auth/google` y `refresh`, siempre con el `tv` vigente de la cuenta. Un token de antes de 4b no trae `tv` y cuenta como 0 (el default de la columna): sobrevive hasta el primer logout de su cuenta. Un `tv` presente que no sea entero ≥ 0 → 401. Un token sin `sid` (antes de 4d) es válido como hasta ahora hasta su `exp`; un `sid` presente que no sea un UUID → 401.

**Handoff (`GET /api/auth/handoff?t&to`, FUERA de v1, sin bearer)**: `t` es un JWS HS256 con `aud = "kura-web-handoff"`, `sub`, `tv`, `jti` y `exp = +60 s`. El `aud` impide que un bearer iOS sirva como `t`, y al revés. Al acuñarlo, el `jti` se registra en `verificationToken` (`identifier = "handoff:" + jti`), así que no hace falta una tabla nueva. La ruta primero valida `to` contra la lista blanca, antes de tocar el token. Después llama a `signIn("otp", { handoff: t })` de Auth.js. El provider Credentials `otp` tiene dos modos: `{ email, code }` (el de siempre, intacto) y `{ handoff }`. En modo `{ handoff }`, `authorize` verifica firma, `aud`, `exp` y el **`DELETE … RETURNING`** de la fila (un solo uso), y además que el `tv` siga siendo el vigente. El consumo vive dentro de `authorize` y no en la ruta porque el callback `POST /api/auth/callback/otp` también es alcanzable directo. El JWS exige `exp`, `jti` y `sub` (`requiredClaims`: uno firmado sin `exp` no vale). Si todo pasa, responde 302 a `to` con la cookie de Auth.js, que lleva el `tv` de la cuenta. **Cualquier** fallo (URL usada, vencida, manipulada, bearer como `t`, `to` fuera de lista, `tv` viejo, navegación cross-site, error del servidor) responde lo mismo: 302 a `/login`, sin cookie. El motivo va **solo al log del servidor**: `[auth/handoff] rid=<uuid> reason=<bad_signature|bad_aud|expired|used|no_user|tv_mismatch|db_error|bad_to|no_token|cross_site>` (un fallo del servidor, `CallbackRouteError`, se loguea como error con `reason=server_error`); el mismo `rid` viaja en `X-Request-Id` de la respuesta. **Mitigación de login-CSRF**: si el navegador manda Fetch Metadata y la navegación no es de primer nivel iniciada por el usuario (`Sec-Fetch-Site` ≠ `none` o `Sec-Fetch-Mode` ≠ `navigate`), se rechaza **sin consumir el token**; sin esos headers (clientes viejos) pasa. El `SFSafariViewController` abierto por la app manda `none` + `navigate`. Las respuestas llevan `Cache-Control: private, no-store` y `Referrer-Policy: no-referrer`, y hay rate limit por IP; el 429 es una página HTML mínima en español ("demasiados intentos"), porque quien la ve es una persona en un navegador. Diseño y riesgos aceptados (token en query string, login-CSRF acotado a 60 s) en `src/authz/handoff.ts` y `.claude/knowledge/state/security.md`.

`requireApiUser(request)` (`src/authz/api.ts`): lee `Authorization: Bearer`, verifica firma/alg/aud/exp/forma de `tv` y `sid`, **relee `users` por `sub` en cada request** con `loadUserForBearer` (`src/auth/user-row.ts`: la misma lista de campos que la cookie, nunca `birthYear`, más `token_version` y, si el token trae `sid`, un **LEFT JOIN a `mobile_session` en la MISMA query** — `id = sid AND user_id = sub`, sin segunda query por request) y devuelve el mismo `CurrentUser` que `requireUser()`. Cuenta borrada, `isMinor`, `tv` ≠ `token_version`, o `sid` cuya sesión no existe / es de otra cuenta / está revocada → 401 aunque la firma sea válida (la revocación es la relectura). `withApi` envuelve **todo** handler v1: `requireBearer` (401 sin DB) → rate limit por `sub` → relectura + `tv` (401 si la fila no está, es menor o el token es de antes del último logout) → `apiContext.run({ user }, handler)` → errores al contrato (con `rid`, método y ruta en el log) → `no-store` + `X-Request-Id`. `getCurrentUser()` consulta `apiContext` **antes** de `auth()`, así que dentro de un request v1 jamás se lee la cookie y `assertUser`/`assertOwnsBacklog`/`assertOwnsUserItem` funcionan sin cambios. `GET /me` pasa por `assertUser()` a propósito para que el puente se ejercite en cada smoke.

`readApiUser(request)` (misma comparación de `tv`) es el gemelo suave para rutas **fuera** de v1 que sirven web y app: hoy solo `/api/avatar/[key]`, que acepta **bearer además de cookie** (la app carga su propia foto sin cookie; mismo gate, mismo 404).

### 2.2 Sign in with Apple / Google (fase 4f, implementado)

Las dos rutas son **públicas** (`withPublicApi`, rate limit por IP como `otp/*`) y responden **exactamente lo mismo que `otp/verify`**: `{ token, user: Me }` (bearer con `sid`, sesión nueva por instalación). Cuenta menor → el mismo `403 forbidden` + `reason: "underage"`. `device` = `{ platform: "ios", name, appVersion }`, el mismo `DeviceSchema` que OTP. Todo fallo del token es **un solo 401** (nunca cuál).

1. `GET /auth/providers` (público, sin bearer) → `{ apple: boolean, google: { clientId: string | null, androidClientId: string | null } | null }`. La app pinta **solo** los botones que funcionan en este deploy: `apple` es `true` siempre salvo el kill-switch `AUTH_APPLE_DISABLED` (verificar un identity token de Apple no necesita llave); `google.clientId` = `GOOGLE_IOS_CLIENT_ID` (iOS lo necesita para `GIDConfiguration`; `null` → sin botón en iOS), `google.androidClientId` = `GOOGLE_WEB_CLIENT_ID` (Android, 2026-09-30: el `serverClientId` que pasa a `GetGoogleIdOption`; `null` → sin botón en Android), `google` es `null` solo si no hay ninguno de los dos (los client ids no son secretos: van dentro de cada build).
2. `POST /auth/apple` `{ identityToken, rawNonce, authorizationCode?, fullName?: { givenName?, familyName? } | null, device }` → `{ token, user: Me }`.
   - `identityToken` se verifica contra el JWKS de Apple (`https://appleid.apple.com/auth/keys`, cacheado por instancia), RS256, `iss = https://appleid.apple.com`, `aud = com.tromwey.kura`, `exp`, y **`nonce` = SHA-256 hex de `rawNonce`** (la app genera `rawNonce`, manda `sha256hex(rawNonce)` en `ASAuthorizationAppleIDRequest.nonce` y el crudo aquí). Cualquier fallo → `401 unauthorized` "No pudimos confirmar tu cuenta de Apple…".
   - Cuenta: `account(provider = "apple", providerAccountId = sub)` → ese usuario. Si no existe y el token trae `email` con `email_verified` (booleano o `"true"`): se **liga** a la cuenta con ese correo si existe, o se **crea** (misma ruta que OTP: `findOrCreateUserByVerifiedEmail` en `src/auth/otp.ts` — badge de fundador y waitlist incluidos), y se inserta la fila `account`. Sin link y sin correo verificado → el mismo 401. Apple solo manda el correo en la PRIMERA autorización: de ahí en adelante manda el `account`.
   - **`fullName` se acepta y se IGNORA (desviación deliberada del brief)**: escribir `users.name` pondría `Me.onboardingComplete = true` y la app se saltaría el paso de onboarding que pide el **año de nacimiento** (el gate de edad F2.2). La app debe **pre-llenar** el campo de nombre del onboarding con `fullName` (Apple solo lo da la primera vez, del lado del cliente); `POST /me/onboarding { name, birthYear }` sigue siendo quien lo guarda.
   - `authorizationCode` (opcional pero **mándalo siempre**): después de responder, el servidor lo intercambia en `https://appleid.apple.com/auth/token` (`client_secret` = JWT ES256 `iss` team, `sub` bundle, `aud` appleid, `kid`) y guarda el `refresh_token` en `account.refresh_token`. Es lo que permite **revocar el vínculo con Apple al borrar la cuenta** (App Store 5.1.1(v), ver `DELETE /me`). Sin las env `APPLE_*` el login funciona igual y el intercambio se salta con log.
   - Kill-switch `AUTH_APPLE_DISABLED=1` → `503 unavailable` "Apple no está disponible por ahora. Entra con tu correo."
3. `POST /auth/google` `{ idToken, nonce?, device }` → `{ token, user: Me }`. **`nonce`** (opcional, string): el nonce **crudo**, mismo esquema que Apple — la app genera `nonce`, manda `sha256hex(nonce)` (hex en minúsculas) como `nonce` en la URL de autorización de Google (Google lo copia tal cual al claim `nonce` del `id_token`) y el crudo aquí; **si viene, el servidor exige `id_token.nonce === sha256hex(nonce)`** (si no coincide = el mismo rechazo que cualquier otro fallo del token). Las apps iOS anteriores no lo mandan y siguen funcionando; **con `aud` = `GOOGLE_WEB_CLIENT_ID` (Android) el `nonce` es obligatorio**: sin él = el mismo rechazo (401 aquí, `422 invalid_proof` en `me/identities/google`). Verifica contra el JWKS de Google (`https://www.googleapis.com/oauth2/v3/certs`), RS256, `iss` ∈ {`https://accounts.google.com`, `accounts.google.com`}, `aud` ∈ {`GOOGLE_IOS_CLIENT_ID`, `GOOGLE_WEB_CLIENT_ID`} (el de iOS, o el web que Android usa como `serverClientId`; `azp` no se revisa), `exp`, y **`email_verified` true obligatorio** (con `email`). Mismo flujo de `account(provider = "google")` + ligado/creación por correo verificado. **Android**: `device.platform = "android"`; el nonce es el mismo esquema — `GetGoogleIdOption.Builder().setNonce(sha256hex(nonce))` y el crudo aquí. Sin ninguno de los dos ids → `503 unavailable` "Google no está disponible por ahora." (y `auth/providers` ya dijo `google: null`). `POST /me/identities/google` (§2.5) acepta las mismas dos audiencias.

**Cuenta ligada**: el correo de la cuenta Kura **nunca cambia** por un proveedor (una cuenta creada con OTP que luego entra con Apple conserva su correo; una creada con Apple guarda el correo que Apple dio, que puede ser un relay `@privaterelay.appleid.com`). Riesgo aceptado del ligado por correo verificado: `state/security.md`.

### 2.3 Sesiones por dispositivo (fase 4d, implementado)

Cada inicio de sesión (OTP, Apple, Google, o el `refresh` que mejora un token legado) crea una fila en `mobile_session` (`id` uuid, `platform`, `device_name`, `app_version`, `created_at`, `last_seen_at`, `revoked_at`) y el bearer lleva su `id` como `sid`. `last_seen_at` se actualiza **como mucho una vez cada ~10 min por sesión**, después de responder (condición en el UPDATE, sin escribir en el camino crítico).

- `GET /me/sessions` → `{ items: [MobileSession] }` — solo las **no revocadas**, `lastSeenAt desc`. `MobileSession = { id, platform, deviceName, appVersion, createdAt, lastSeenAt, current: boolean }` (`current` = la sesión del bearer que pregunta; un bearer legado sin `sid` ve todas en `false`). `deviceName` es el texto que mandó la app: solo lo ve su dueño.
- `DELETE /me/sessions/{id}` → `204`. Revoca esa sesión y **borra sus `device_token`** (una transacción). El siguiente request de esa app es `401`. **La sesión actual también se puede revocar** (este mismo bearer muere). Ajena, inexistente, malformada **o ya revocada** = el **mismo 404** "No encontramos esa sesión…" (la app debe tratar un 404 aquí como "ya no está").
- `POST /auth/logout` sigue siendo "en todos lados" (§2.1 paso 4).

**La migración 0029 está aplicada desde el 2026-09-24 y su switch (`MIGRATION_0029_LIVE`) se retiró del código el 2026-10-01**: todo login acuña con `sid`, y `GET /me/sessions`, `DELETE /me/sessions/{id}`, `PUT|DELETE /me/devices/{token}` y `PATCH /me { notifyFollowers }` ya **no** tienen el `503 unavailable` "todavía no disponible" de la transición (una build vieja que aún lo tolere no se rompe: simplemente no vuelve a verlo).

### 2.4 Push: dispositivos y avisos (fase 4e, implementado)

- `PUT /me/devices/{token}` `{ environment?: "sandbox" | "production", provider?: "apns" | "fcm" }` → `204`. `provider` (2026-09-30) por defecto `"apns"` — las builds iOS no cambian nada.
  - **`apns`** (iOS): `environment` **obligatorio** (falta o inválido → `400 invalid` + `fields.environment`); `token` = el token de APNs en **hex, 64..200 caracteres** (se guarda en minúsculas). `environment` = `sandbox` en builds de Xcode/Debug, `production` en TestFlight/App Store.
  - **`fcm`** (Android): el token de registro de FCM **tal cual** (`FirebaseMessaging.getInstance().token`; `[A-Za-z0-9_:-]`, 32..1024; se guarda sin tocar mayúsculas), **percent-encoded** en el path (`:` → `%3A` está bien, `Uri.encode`). `environment` se ignora (se guarda `production`). La migración 0035 está aplicada (2026-09-30) y su switch se retiró el 2026-10-01: el `503 unavailable` + `reason: "fcm_pending"` de la transición **ya no se emite** (el cliente puede conservar su rama de reintento; nunca la verá).
  - Token de la forma equivocada para su `provider` → `400 invalid` + `fields.token`; `provider` desconocido → `fields.provider`. Upsert: si el token ya era de **otra cuenta**, pasa a la actual (el teléfono cambió de dueño o de sesión); queda ligado a la sesión del bearer (`sid`), así que revocar esa sesión o hacer logout lo borra.
- `DELETE /me/devices/{token}` → `204` idempotente, **sin body** y sin `provider` (la forma del token dice cuál probar: hex = APNs en minúsculas, lo demás = FCM tal cual); solo borra si el token es del caller (ajeno o desconocido = el mismo 204). Ninguna de las dos formas → `400` + `fields.token`.
- `Me.notifyFollowers: boolean` (default `true`) + `PATCH /me { notifyFollowers }` (booleano estricto como `notifyRecap`: `"no"` → 400 `fields.notifyFollowers`). Preferencia propia: nunca en `Person`.
- **Avisos que envía el servidor** (APNs HTTP/2 a `api.push.apple.com` o `api.sandbox.push.apple.com` según `environment`, `apns-topic: com.tromwey.kura`, `apns-push-type: alert`; payload `{ aps: { alert: { title, body? }, sound: "default" }, kura: { … } }`):
  - **Estreno** (cron diario de estrenos, a quien le sale el correo — `notifyReleases`, guardado antes del estreno, una sola vez por título): `title` = "{título} ya salió ✦", `body` = la primera línea del correo ("Hoy sale {título}, de {artista}." en álbum; "Hoy sale {título}." en video), `kura: { type: "release", titleId }`.
  - **Nuevo seguidor** (solo cuando la arista es NUEVA, no en un re-follow idempotente; solo si quien sigue es un perfil **público con handle** y el seguido tiene `notifyFollowers`; máximo **uno por par cada 24 h**, así que dejar de seguir y volver a seguir no vuelve a sonar): `title` = "@{handle} te sigue", sin `body`, `kura: { type: "follower", handle }`.
- **Android (FCM HTTP v1, desde 0035)**: los mismos avisos, por `POST https://fcm.googleapis.com/v1/projects/{project_id}/messages:send` con un access token OAuth2 de la cuenta de servicio (`FCM_SERVICE_ACCOUNT_JSON`). Mensaje: `{ token, notification: { title, body? }, data: { type, titleId? | handle? }, android: { priority: "high" } }` — **`data` es un mapa de strings** (lo que en APNs va bajo `kura` aquí va plano en `data`: `type = "release"` + `titleId`, o `type = "follower"` + `handle`). Con la app en primer plano el SDK no pinta la `notification`: llega a `onMessageReceived` y la app decide; en segundo plano la pinta el sistema en el canal por defecto del manifest (`com.google.firebase.messaging.default_notification_channel_id`) y el `data` viaja en los extras del intent al tocarla.
- Un token que APNs responde `410` o `BadDeviceToken`/`Unregistered`, o que FCM responde `404` o `UNREGISTERED`, se borra solo. Sin las env `APPLE_TEAM_ID`/`APPLE_KEY_ID`/`APPLE_PRIVATE_KEY` (iOS) o `FCM_SERVICE_ACCOUNT_JSON` (Android) el envío de ese proveedor es un no-op con log `[push] …`: los endpoints de registro funcionan igual y nada falla.
- `GET /me/notifications` → sigue sin existir (sin modelo de bandeja).

### 2.5 Conectar Apple/Google y fusionar cuentas (fase 4g, implementado)

Todo con bearer (`withApi`); ningún endpoint acepta un `userId`. **La cuenta del bearer es el DESTINO** (se queda); la otra, el **ORIGEN**, se absorbe y desaparece. Sin migración: vínculos en `account` (PK `(provider, provider_account_id)`), un solo uso en `verificationToken`, JWS propio.

**Identidades**

1. `GET /me/identities` → `200 { email, emailIsRelay, providers: [{ provider: "apple" | "google", linked: boolean }] }`. `email` = el correo de la cuenta (siempre es una entrada: código por correo). `emailIsRelay` = el correo es un relay de "Ocultar mi correo" de Apple (`@privaterelay.appleid.com`): la app lo explica antes de ofrecer desconectar Apple. `providers` lista solo los proveedores **habilitados en este deploy** (misma regla que `auth/providers`: Apple salvo `AUTH_APPLE_DISABLED`, Google con `GOOGLE_IOS_CLIENT_ID` **o** `GOOGLE_WEB_CLIENT_ID` — basta uno de los dos; `POST /me/identities/google` acepta un `idToken` con `aud` de cualquiera de ellos, §2.2); `linked` = hay fila `account` de ese proveedor para esta cuenta.
2. `POST /me/identities/apple` `{ identityToken, rawNonce, authorizationCode? }` · `POST /me/identities/google` `{ idToken, nonce? }` (`nonce` como en §2.2) — mismas verificaciones que §2.2, sin `device`:
   - `200 { linked: true }` — quedó conectado, o ya era de ESTA cuenta (idempotente).
   - `409 { error: { code: "conflict", message, reason: "linked_elsewhere", mergeToken, source: MergeSource } }` — la identidad es de **otra** cuenta Kura: por su fila `account`, o (sin fila) porque su correo verificado es el de otra cuenta (la cuenta a la que ese proveedor entraría hoy; en ese caso el servidor la liga a ESA cuenta, como haría el login, y el vínculo pasa a la tuya con la fusión). El token del proveedor ya probó la propiedad: el `mergeToken` va **dentro del envelope de error**, junto a `reason`.
   - `409 { error: { code: "conflict", message, reason: "provider_already_linked" } }` — esta cuenta ya tiene OTRA identidad de ese proveedor (otro `sub`). Sin `mergeToken`.
   - `422 { error: { code: "invalid", message, reason: "invalid_proof" } }` — token rechazado (firma, `aud`, `exp`, nonce, `email_verified` de Google…): un solo cuerpo por proveedor, falle lo que falle. **No 401** (ver §1).
   - `400 invalid` + `fields` — body mal formado. `503 unavailable` — proveedor apagado. `404` — proveedor desconocido en el path.
   - Apple: `authorizationCode` se intercambia DESPUÉS de responder (como el login) → refresh token en la fila `account`, para poder revocar.
3. `DELETE /me/identities/{apple|google}` → `204` (idempotente). Borra las filas `account` de ese proveedor de esta cuenta; Apple: revoca el refresh token después de responder (best-effort). Permitido (el correo sigue siendo entrada) **salvo** Apple cuando el correo de la cuenta es un relay de Apple y no hay otro proveedor conectado → `409 { error: { code: "conflict", message, reason: "last_way_in" } }`, sin tocar nada (al revocar Apple el relay podría dejar de reenviar los códigos y la cuenta quedaría sin entrada). Proveedor desconocido → `404`.

**Probar que el ORIGEN es tuyo** — los tres caminos terminan en `{ mergeToken, source }`:

- (a/c) El `409 linked_elsewhere` de arriba (Apple o Google).
- (b) Código por correo:
  - `POST /me/merge/otp/request { email }` → **`204` siempre**, exista o no una cuenta con ese correo, y aunque sea el propio (sin oráculo: el mismo row y el mismo cooldown en los dos casos; el correo solo sale si hay OTRA cuenta con ese correo, y se manda después de responder). Cooldown de 60 s por (tu cuenta, correo) → `429 rate_limited` con **`reason: "cooldown"`** y `retryAfterSeconds` = la espera real (≤ 60; antes siempre 60 y sin `reason`); además, **máximo 3 códigos por hora por correo destino**, sumando TODAS las cuentas que lo pidan → `429 rate_limited` con **`reason: "hourly_cap"`** y `retryAfterSeconds` hasta que el más viejo cumpla la hora (2026-10-01, ciclo 3: mismos nombres que `auth/otp/request`; un 429 SIN `reason` aquí es el limitador de escrituras del bearer). **Ronda 5**: si el correo del código no se pudo enviar (el proveedor lo rechazó), el código se retira y esa emisión deja de contar para el tope de 3; el 429 dentro de ese minuto llega con `reason: "hourly_cap"` y `message` "Se pidieron demasiados códigos para ese correo. Podrás pedir otro en {tiempo}." (`{tiempo}` = `retryAfterSeconds` como "45 s" / "3 min") — **solo `cooldown` permite decir "revisa tu correo"**, igual que en el login. Los dos límites valen igual exista o no la cuenta. `400 invalid` si el correo no es válido. El código es de 6 dígitos, vive 10 min, 5 intentos (atómicos: intentos en paralelo no pasan de 5), y **no sirve como código de login** (identificador `merge:<tuId>:<correo>`; `verifyOtp` rechaza ese espacio de nombres).
  - `POST /me/merge/otp/verify { email, code }` → `200 { mergeToken, source }`, o **`422 { error: { code: "invalid", message: "El código es incorrecto o ya venció. Revísalo o pide otro.", reason: "invalid_proof" } }`** — el MISMO para código malo, vencido, quemado, o sin cuenta con ese correo.

`MergeSource = { handle: string | null, name: string | null, email: string, isPublic: boolean, counts: { titles, collections, reviews, followers, following } }` (enteros ≥ 0). Lleva el correo del origen: quien lo pide acaba de probar que es suyo. `isPublic` = el origen era visible públicamente (público y con handle); si es `false` y tu cuenta es pública, **avisa**: su actividad por título y sus reseñas se verán en tu perfil (sus colecciones llegan como Privadas). La app lo muestra antes de confirmar y **avisa que, tras fusionar, el correo del origen deja de ser una entrada** (un código a ese correo crearía una cuenta nueva y vacía).

`mergeToken` = JWS HS256 (`AUTH_SECRET`), `aud = "kura-merge"`, `sub` = tu cuenta, `src` = el origen, `jti`, **10 minutos, un solo uso** (`jti` en `verificationToken` como `merge-token:<jti>`, se quema con `DELETE … RETURNING`). Opaco para la app: guárdalo solo en memoria.

**Fusionar**

- `POST /me/merge { mergeToken }` → `200 { user: Me }` (el `Me` del destino, ya con lo absorbido). **Reintento (2026-10-01, ciclo 3)**: si responde `500` (fallo transitorio del servidor) el `mergeToken` NO se quemó — se puede reintentar con el MISMO token hasta su `exp` (10 min), sin pedir otro código. `409 merge_token_invalid` y `403 underage` sí lo dejan quemado: hay que volver a probar la otra cuenta.
  - Token vencido, ya usado, de otra cuenta, mal firmado, o su origen ya no existe → **`409 { error: { code: "conflict", message: "El permiso para fusionar venció o ya se usó. Vuelve a confirmar la otra cuenta.", reason: "merge_token_invalid" } }`** (uno solo; no 401: tu bearer es válido).
  - Origen o destino menor de edad → `403 forbidden` + `reason: "underage"`, sin tocar nada.
  - Body sin `mergeToken` → `400 invalid` + `fields.mergeToken`.
  - Una transacción (`db.batch`): todo o nada. Después, las sesiones del origen mueren (su `user` se borra: sus bearers y cookies son 401 en la siguiente relectura).

**Qué pasa con los datos** (detalle y guardrail en `src/modules/account/merge.ts` / `merge-coverage.ts`):

- Identidad del destino intacta (`email`, `handle`, `name`, año de nacimiento, `isPublic`, foto salvo que no tenga). `isFounder` = destino OR origen (insignia de cohorte).
- Proveedores (`account`) → al destino (si ya tenía ese proveedor con otro `sub`, quedan los dos y `linked` sigue `true`). Colecciones y membresías → al destino (no hay nombre único: puede quedar un "Obsesiones" repetido); si el origen era privado o sin handle, sus colecciones llegan como **Privadas**.
- Estado por título, choque: gana el **estado más avanzado** (`on_my_radar` < `in_progress` < `completed`; empate = el del destino) con su `statusChangedAt`; veredicto del destino si lo tiene, si no el del origen; obsesión = OR con la fecha más antigua; `addedAt` = la más antigua.
- Reseñas, choque: se queda la del destino y la del origen se borra (con sus reportes). Una reseña oculta sigue oculta.
- Seguidos y bloqueos: se mueven en ambos sentidos, sin duplicados ni aristas contigo mismo; un follow entre tú y alguien que (ahora) bloqueas o te bloquea se borra. **Seguidores** del origen pasan a ti solo si tu perfil es público y tiene handle (si no, se pierden: nadie sigue a un perfil privado).
- Foto: la del origen solo si el destino no tiene. Sesiones, tokens de push del origen: mueren. Medidor de recos del mes: se SUMA.

## 4. Endpoints

Todos bajo `/api/v1`, todos con bearer **salvo las rutas públicas** (`withPublicApi`, rate limit por red, 429 `ip_limit`): `POST /auth/otp/request`, `POST /auth/otp/verify`, `POST /auth/apple`, `POST /auth/google`, `GET /auth/providers` y `GET /invites/{token}` (esta última lee el bearer si viene, para aplicar bloqueos, pero no lo exige). El resto de `auth/*` (`refresh`, `logout`, `web-session`) y `POST /invites/{token}/join` SÍ llevan bearer. Entre paréntesis, el módulo que se reutiliza.

**Auth** — ver §2.1 (OTP, refresh, logout, web-session) y §2.2 (`auth/providers`, `auth/apple`, `auth/google`). **Sesiones y dispositivos** — ver §2.3 (`GET /me/sessions`, `DELETE /me/sessions/{id}`) y §2.4 (`PUT|DELETE /me/devices/{token}`, APNs o FCM). **Identidades y fusión** — ver §2.5 (`GET /me/identities`, `POST|DELETE /me/identities/{apple|google}`, `POST /me/merge/otp/request`, `POST /me/merge/otp/verify`, `POST /me/merge`).

- `PATCH /me` `{ name?, preferredService?, notifyReleases?, notifyRecap?, notifyFollowers?, isPublic?, followListsVisibility? }` → `Me` re-leído (`modules/account/profile.ts` `updateProfile`, misma validación que las cinco actions; campo ausente = intacto; body vacío = no-op que devuelve `Me`). `notifyRecap` (fase 4b) es un booleano estricto como `notifyReleases`: `"no"`, `0` o `null` → `400 invalid` + `fields.notifyRecap`. Reglas: forma estricta `YYYY-MM-DD`, día real del calendario, año ≥ 1900, no posterior a hoy (UTC+14); si no → `400 invalid` + `fields.birthDate` ("Esa fecha no es válida."), sin escribir nada. Un 29 de febrero cumple el 1 de marzo en año no bisiesto. Edad < 13 → la cuenta queda bloqueada (`is_minor`; este bearer y todo login futuro son 401) y responde `403 forbidden` + `reason: "underage"`; ≥ 13 → `200` + `Me` (`onboardingComplete: true`).

Esta cuenta no puede entrar."}}`.

Con `n = año actual (en UTC+14) − birthYear`: **`n ≥ 14` → pasa** como antes; **`n ≤ 12` → `403 underage`** como antes (bloquea); **`n = 13` (el año no distingue 12 de 13) → `400 invalid` + `fields.birthYear` = "Necesitamos tu fecha de nacimiento completa. Actualiza kura y vuelve a intentarlo."**, sin escribir nada y SIN bloquear (reintentar con `birthDate` funciona). Fuera de 1900..año actual → `400` + `fields.birthYear` ("Ese año no es válido."); no entero → `400` + `fields.birthYear` (zod). **Si llegan ambos, manda `birthDate`** y `birthYear` se ignora (un `birthDate` inválido NO se rescata con el año). Ninguno de los dos → `400` + `fields.birthDate` ("Escribe tu fecha de nacimiento."). `birthDate` de más de 10 caracteres o no-string → `400` + `fields.birthDate`.

La app ofrece "guardar en" después (`PUT /collections/{id}/titles/{titleId}` le agrega membresía sin tocar el estado). Orden: id desconocido en el catálogo (o no-UUID) → `404`; la regla de estreno corre **antes** de crear (un `409` no deja nada); `mark: null` sobre un título sin estado → **`404`** (quitar la marca de algo que no está en la biblioteca no crea nada). `DELETE /me/titles/{id}` lo quita como a cualquier otro. **La reseña se borra con la reacción (founder, 2026-10-01)**: una reseña solo existe mientras el título tenga reacción (`mark` ∈ `obsessed` \| `liked`, o un "no me gustó" puesto en la web). Un PUT que deje el título SIN reacción — **`mark: "completed"`** o **`mark: null`** — **borra la reseña propia de ese título en la misma transacción** que el cambio de estado (y con ella sus reportes: `report.target_review_id` cascadea), y el `TitleState` de la respuesta trae **`reviewId: null`** (esa es la señal; no hay campo nuevo: `reviewId` no-nulo antes + `null` en la respuesta = se borró). `obsessed` ⇄ `liked` NO la borra. Ejemplo: `PUT …/mark {"mark":"completed"}` sobre un título con reseña → `200 {"titleId":"…","mark":"completed","savedAt":"…","reviewId":null}`; a partir de ahí `GET /titles/{id}` ya no la trae y `PUT …/review` responde `409 reaction_required` hasta volver a reaccionar. No hay deshacer en servidor: volver a marcar NO restaura el texto (la app debe avisar antes o conservar el borrador localmente). No existe `DELETE …/mark`: quitar la marca es `PUT { "mark": null }`.
- `PUT /me/titles/{id}/review` `{ body, hasSpoiler }` → `Review` (`assertOwnsUserItem` + `modules/reviews/write.ts` `saveReview`: exige reacción previa → `409` + `reason: "reaction_required"`; enlaces → 400; 1..280 → 400; álbum nunca lleva spoiler; editar conserva `hiddenAt`). **Exige onboarding completo: `403 forbidden` + `reason: "onboarding_required"`** (F2.2, 2026-10-01; se decide sobre la fila del que llama ANTES de mirar el título). `DELETE` → `204` (idempotente, nunca gateado). La regla "reacciona primero" se decide además DENTRO de la transacción del guardado (tras el lock del título): si la reacción se quitó en paralelo, el guardado responde el mismo `409 reaction_required` y no deja reseña.
- `DELETE /me/titles/{id}` → `204` (`removeTitleFromLibrary`: todas las membresías + estado + reseña; idempotente).
- `PUT|DELETE /me/titles/{id}/episodes/{key}` → `501 unsupported` (sin modelo; la app lo guarda local). Con bearer a propósito: sin token sigue siendo 401.
